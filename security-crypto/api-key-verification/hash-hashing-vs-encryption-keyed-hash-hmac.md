# "해시 암호화"가 뭐고, 거기서 key는 어떻게 쓰일까?

## 먼저 용어 바로잡기: 해시는 사실 "암호화"가 아니에요

**해싱(hashing)은 암호화(encryption)가 아니에요.** 둘 다 암호학(cryptography) 분야이긴 하지만 목적과 되돌릴 수 있는지 여부가 완전히 달라요.
- **암호화**: 원문(A) → 암호문(B)으로 바꾸되, **키(key)만 있으면 다시 A로 되돌릴 수 있음(양방향, reversible)**.
- **해싱**: 원문(A) → 고정 길이 값(다이제스트, digest)으로 바꾸는데, **절대 원문으로 되돌릴 수 없음(단방향, one-way)**.

일상에서 "해시 암호화"라고 많이 불러서 헷갈리기 쉬운데, 정확히는 "해시 함수(hash function)"라고 부르는 게 맞아요. 다만 워낙 관용적으로 쓰이는 표현이라, 질문 의도를 살려서 아래에서는 "해시"와 그 안에 key를 쓰는 방식(HMAC)을 설명할게요.

## 다섯 살에게 설명하듯

**일반 해시**는 서류를 **분쇄기(shredder)**에 넣는 것과 같아요. 넣으면 항상 같은 방식으로 잘게 썰리지만(같은 입력 → 같은 출력), 한번 썰리면 원본으로 절대 못 돌려요. 그리고 누구나 이 분쇄기를 쓸 수 있어요 — 열쇠가 필요 없어요.

**key를 쓰는 해시(HMAC)**는 그 분쇄기에 **비밀 재료(key)를 섞어서** 종이를 써는 거예요. 나만 아는 비밀 재료를 섞었기 때문에, 나중에 "이 잘린 조각들, 진짜 내가(비밀 재료를 아는 사람이) 썬 게 맞아?"를 확인할 수 있어요. 비밀 재료를 모르는 사람은 똑같이 흉내 낸 조각을 못 만들어요.

## 기술적으로 풀어보면

### 1. Key 없는 일반 해시 함수 (SHA-256 등)

- 입력이 뭐든(1글자든 1GB든) 항상 **고정된 길이의 출력**을 내놓아요.
- 같은 입력 → 항상 같은 출력 (결정론적, deterministic).
- 용도: **무결성(integrity) 검증**. 예) 파일 다운로드 후 체크섬(checksum) 비교, Git 커밋 해시.
- 문제점: **키가 없어서 아무나 재현할 수 있어요.** 그래서 "이 값이 진짜 특정 발신자가 만든 게 맞는지(인증, authenticity)"는 보장 못 해요. 중간에서 누가 메시지와 해시값을 통째로 바꿔치기해도 받는 쪽은 구분할 수 없어요.

### 2. Key를 쓰는 해시 = MAC / HMAC

이 문제를 해결하려고 **비밀 키(secret key)를 메시지와 함께 섞어서** 해시하는 방식이 나왔어요. 이걸 **MAC(Message Authentication Code)**이라 부르고, 그중 해시 함수를 이용해 만드는 가장 널리 쓰이는 방식이 **HMAC(Hash-based MAC)**이에요.

**HMAC이 key를 사용하는 구체적인 과정** (예: HMAC-SHA256):

1. 비밀 키를 두 가지 패딩 값과 각각 XOR 연산해서 **`ipad`(inner pad)**용 키와 **`opad`(outer pad)**용 키, 두 버전을 만들어요.
2. **1차 해싱**: `SHA256(innerKey + 메시지)` → 내부 해시값(internal hash)을 얻어요.
3. **2차 해싱**: `SHA256(outerKey + 1차 해시값)` → 이게 최종 HMAC 결과예요.
4. 즉, **키를 메시지에 두 번(안쪽·바깥쪽) 섞어 넣는 이중 해싱 구조**예요. 단순히 "키+메시지를 한 번만 붙여서 해싱"하지 않는 이유는, 그렇게 하면 **길이 확장 공격(length extension attack)**이라는 취약점이 생기기 때문이에요 — 공격자가 원본 메시지를 몰라도 해시값 뒤에 데이터를 추가로 이어붙여서 유효한 새 해시를 만들어낼 수 있는 공격이에요. 이중 해싱 구조가 이걸 막아줘요.

### 3. Key가 있으면 무엇이 달라지는가

- **재현 불가능성**: 키를 모르는 사람은 같은 메시지를 넣어도 절대 같은 HMAC 값을 만들 수 없어요.
- 그래서 받는 쪽이 "이 메시지 + 이 HMAC 값"을 받으면, **①메시지가 중간에 변조되지 않았는지(무결성)**와 **②정말로 이 키를 아는 사람(발신자)이 보낸 게 맞는지(인증)**를 동시에 검증할 수 있어요. 일반 해시는 ①만 되고 ②는 안 돼요.
- 속도 면에서도 대칭키 암호화보다 훨씬 빠르고 가벼워서(출력 크기 고정, 계산 단순), 실무에서 메시지 인증 용도로 암호화 대신 HMAC을 많이 써요.

### 4. 실무에서 어디에 쓰이나

- **API 요청 서명**: AWS Signature V4, 웹훅(webhook) 페이로드 서명 등 — "이 요청, 진짜 우리 서버가 발급한 키를 가진 곳에서 온 거 맞아?"를 확인.
- **JWT(JSON Web Token)의 `HS256` 알고리즘**: 토큰 내용 + 서버만 아는 비밀키로 HMAC-SHA256 서명을 만들어서, 클라이언트가 토큰 내용을 몰래 바꿔도 서명 검증에서 걸러내요.
- **TLS/IPsec 같은 통신 프로토콜**: 데이터가 전송 중 변조되지 않았는지 확인하는 무결성 체크에 HMAC-SHA-256/384/512가 표준으로 쓰여요.

### 참고: 비밀번호 저장은 다른 얘기예요

비밀번호를 저장할 땐 일반 해시나 단순 HMAC이 아니라 **bcrypt, scrypt, Argon2** 같은, 일부러 계산을 느리게 만든 **전용 해시 함수**를 써요. HMAC은 "빠르고 검증 가능함"이 장점인데, 비밀번호는 오히려 "느려서 무차별 대입(brute-force)이 어려워야" 안전하기 때문이에요. (다만 PBKDF2 같은 키 유도 함수 내부에는 HMAC이 반복적으로 쓰이기도 해요.)

## 요약 표

| 구분 | 일반 해시 (SHA-256) | 키 사용 해시 (HMAC) |
|---|---|---|
| Key 필요 여부 | 불필요 | **필요 (비밀 키)** |
| 검증 가능한 것 | 무결성만 | 무결성 + 인증(발신자 확인) |
| 재현 가능성 | 누구나 재현 가능 | 키를 아는 사람만 재현 가능 |
| 대표 용도 | 체크섬, 커밋 해시 | API 서명, JWT(HS256), TLS 무결성 |

## 한 줄 요약

> 일반 해시는 "**아무나 확인 가능한 지문**"이고, HMAC처럼 key를 쓰는 해시는 "**비밀 도장을 찍어야 진짜라고 인정되는 지문**"이에요. Key는 메시지 앞뒤로 두 번(ipad/opad) 섞여 들어가서, 그 키를 모르면 절대 똑같은 결과를 위조할 수 없게 만들어줘요.
