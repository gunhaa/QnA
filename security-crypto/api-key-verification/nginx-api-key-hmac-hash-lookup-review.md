# nginx API Key 인증에 HMAC 해시 + DB/캐시 조회 방식 검토

## 결론부터

**전반적으로 좋은 설계 방향이에요.** HMAC 연산 자체는 걱정할 만큼 무겁지 않고요. 다만 "왜 굳이 HMAC을 쓰는지", "타이밍 공격은 괜찮은지", "캐시 무효화는 어떻게 할지" 몇 가지는 짚고 넘어가는 게 좋아요.

## Q1. HMAC의 연산 비용은 큼?

**아니요, 거의 무시할 수준이에요.** 실측 벤치마크에 따르면 HMAC-SHA256 하나를 계산하는 데 걸리는 시간은 **약 0.18ms**(m6i.xlarge 기준) — 즉 1000분의 1초도 안 되는 수준이에요. 초당 1,400 요청을 처리하는 서버 기준으로도 CPU 코어 1개의 **25%** 정도만 써요.

### 다섯 살에게 설명하듯

지난번에 배운 워커의 이벤트 루프 기억하시죠? HMAC 계산은 **아주 짧은 암산 문제**예요. 웨이터가 손님 카드를 보고 "3 더하기 5는?" 하고 즉석에서 계산하는 정도라, 옆 테이블(다른 연결)에 거의 지장을 안 줘요. 반면 DB에 물어보러 주방 뒤 창고까지 걸어갔다 오는 것(네트워크 I/O)이 훨씬 오래 걸려요.

### 기술적으로

- HMAC은 **I/O가 아니라 순수 CPU 연산**이에요. 지난 대화에서 다룬 "블로킹 함수가 이벤트 루프를 멈춘다"는 우려와는 종류가 달라요 — 애초에 대기(wait)할 게 없고 그냥 계산만 하니, `access_by_lua_block`에서 `ngx.hmac_sha256(secret, api_key)`를 매 요청마다 호출해도 **이벤트 루프를 유의미하게 막지 않아요.**
- 진짜 병목은 거의 항상 **DB/캐시 네트워크 왕복(round-trip)**이지, HMAC 계산이 아니에요. 그러니 "HMAC이 부담될까봐 캐싱한다"는 생각보다는, "**DB 조회 자체를 캐싱한다**"는 관점으로 접근하는 게 맞아요.

## Q2. 애초에 API Key에 HMAC까지 써야 함? 그냥 SHA-256 해시만 저장하면 안 됨?

여기서 **비밀번호(password)와 API 키(API key)의 성격 차이**를 구분해야 해요.

- **비밀번호**: 사람이 만들어서 엔트로피(entropy, 무작위성)가 낮아요(`password123` 같은 거). 그래서 오프라인 무차별 대입(brute-force)에 취약하고, **일부러 느리게 만든** bcrypt/scrypt/Argon2를 써야 해요.
- **API 키**: 서버가 발급하는 **고엔트로피 랜덤 값**(예: 32바이트 랜덤 문자열)이에요. 이건 애초에 무차별 대입 자체가 사실상 불가능한 키 공간이라, OWASP도 **API 키에는 굳이 느린 해시(bcrypt 등)를 쓸 필요가 없다**고 명시해요 — 오히려 "비밀번호용 느린 해시는 API 키에는 안 맞는다(wrong)"고 표현할 정도예요.

그럼 왜 굳이 HMAC(키 있는 해시)을 쓰냐면:

- **그냥 SHA-256(키 없음)**: DB가 통째로 유출되면, 공격자는 저장된 해시값 자체는 뒤집을 수 없지만(고엔트로피라 레인보우 테이블도 무의미), 만약 시스템 어딘가에 실제 원본 API 키가 노출되는 다른 경로가 있다면 그걸로 검증 시도를 할 수 있어요.
- **HMAC(비밀 키 있음)**: DB 덤프만으로는 검증 로직 자체가 성립하지 않아요. 왜냐면 **HMAC 비밀 키(pepper라고도 불림)는 DB가 아니라 별도 위치(nginx 환경변수, Vault, KMS 등)에 보관**되니까요. 즉 "**DB가 털려도, 이 키(pepper)까지 같이 털리지 않는 한 아무 소용 없다**"는 **계층 방어(defense in depth)**를 하나 더 얹는 거예요. OWASP 비밀번호 저장 가이드에서도 해시값을 한 번 더 HMAC으로 감싸고 그 HMAC 키를 별도 보관하는 방식을 pepper 전략으로 소개해요.

→ **결론**: 지금 설계(HMAC 후 저장)는 정당해요. 다만 **HMAC 비밀 키를 DB와 완전히 분리된 곳에 보관하는 것**이 이 방식의 핵심 전제예요. 만약 그 키도 DB나 같은 서버 설정 파일에 같이 있다면, 굳이 HMAC을 쓰는 의미가 많이 줄어들어요.

## Q3. API 키를 원문 그대로 비교(`==`)하지 않고 해시로 저장해서 비교하면 타이밍 공격(timing attack)은 안전함?

이 부분이 흥미로운 지점인데, **설계 자체가 타이밍 공격에 자연스럽게 어느 정도 강해요.** 이유는 **눈사태 효과(avalanche effect)** 때문이에요.

- 일반적인 타이밍 공격은 "비교 함수가 첫 바이트부터 순서대로 비교하다가 틀리면 바로 리턴한다"는 점을 악용해요. 그러면 공격자가 응답 시간 차이를 재서 "어느 바이트까지는 맞았다"를 한 글자씩 알아낼 수 있어요.
- 그런데 지금 구조는 **클라이언트가 원문 API 키를 보내면, nginx가 그걸 HMAC으로 변환한 뒤에 그 결과값으로 DB/캐시를 조회**하는 방식이에요. HMAC은 입력이 1비트만 달라져도 출력이 완전히 무작위로 바뀌는 눈사태 효과가 있어서, **"원문 키의 한 글자를 맞혔다고 해서 최종 해시값이 조금이라도 비슷해지지 않아요.** 그래서 설령 최종 비교(DB 인덱스 조회, 문자열 비교)가 타이밍에 민감한 방식이더라도, 공격자는 그 타이밍 차이로부터 "원문 API 키 어디가 맞았는지"를 전혀 유추할 수 없어요.
- ⚠️ 단, 이건 **"공격자가 원문 키를 추측해서 보내는" 시나리오**에 대한 이야기예요. 만약 반대로 **웹훅(webhook) 서명 검증처럼 공격자가 메시지와 함께 "이게 정답 HMAC 값이야"라며 해시값 자체를 직접 들이미는 시나리오**라면 얘기가 달라져요. 그 경우엔 서버가 로컬에서 계산한 HMAC과 공격자가 보낸 HMAC 값을 **바이트 단위로 직접 비교**하게 되는데, 이때는 진짜 고전적인 타이밍 공격이 성립할 수 있어서 **반드시 상수 시간 비교(constant-time compare)**를 써야 해요.
- 지금 케이스(API 키 → 서버가 HMAC 계산 → DB 조회)는 후자보다 안전한 구조이긴 하지만, **비용이 거의 안 드니 그냥 방어적으로 상수 시간 비교를 습관화**하는 걸 추천해요. Lua에서는 OpenSSL의 `CRYPTO_memcmp` 계열을 바인딩한 라이브러리(`lua-resty-openssl` 등)를 쓰거나, 단순 비교라면 두 값을 다시 한번 해시해서 비교하는 "더블 HMAC(double HMAC)" 트릭도 있어요.

## Q4. 캐시 구조는 어떻게 짜는 게 좋을까? (제안)

말씀하신 "DB 혹은 캐시에 저장해 비교"를 3단 계층으로 구성하면 효율이 좋아요:

1. **1차: 워커 로컬 캐시 (`ngx.shared.dict`)**: 같은 워커 프로세스 안에서는 메모리 접근이라 네트워크 왕복이 아예 없어요. TTL을 짧게(예: 30초~1분) 둬서 키 폐기(revoke) 반영 지연을 최소화해요.
2. **2차: 분산 캐시 (Redis)**: 워커 간, 서버 간 공유되는 캐시. DB까지 안 가고 여기서 대부분의 조회가 끝나게 하는 게 목표예요.
3. **3차: DB (최종 소스)**: 캐시 미스일 때만 조회. 조회 결과는 다시 1·2차 캐시에 채워 넣어요(cache-aside 패턴).

⚠️ **키 폐기(revocation) 시 주의**: 캐시에 "유효함(valid)"이라고 저장해뒀는데 그 사이 관리자가 키를 폐기하면, TTL이 만료될 때까지 계속 유효한 것처럼 통과될 수 있어요. 중요한 보안 이벤트(키 폐기)는 TTL 만료를 기다리지 말고 **캐시를 즉시 무효화(invalidate)하는 이벤트를 발행**하거나, 애초에 "유효함"보다 TTL을 짧게 두는 쪽으로 균형을 잡으세요.

## 실전 체크리스트

| 항목 | 권장 사항 |
|---|---|
| 해시 알고리즘 | HMAC-**SHA256** 이상 (SHA-1은 지양) |
| HMAC 비밀 키(pepper) 보관 위치 | DB와 분리된 곳 (env var, Vault, KMS) — **DB에 같이 두면 의미 없음** |
| API 키 자체의 엔트로피 | 충분히 랜덤하게 발급(예: 32바이트 이상) — 짧거나 예측 가능하면 HMAC을 써도 무의미 |
| 최종 비교 방식 | 가능하면 상수 시간 비교 사용 (방어적 조치) |
| 전송 구간 | HTTPS/TLS 필수 (API 키가 헤더에 평문으로 오가므로) |
| 캐시 계층 | `ngx.shared.dict`(로컬) → Redis(분산) → DB(최종) |
| 키 폐기 반영 | 캐시 TTL 짧게 + 가능하면 즉시 무효화 경로 마련 |
| 키 로테이션 | HMAC 비밀 키를 교체하면 기존 저장된 해시값이 전부 무효화됨 — 버전 필드(`key_version`)를 같이 저장해서 점진적 마이그레이션 가능하게 설계 |
| 레이트 리미팅 | 해시가 안전해도 무차별 대입/스캐닝 자체를 막기 위해 `limit_req` 등 병행 |

## 요약

> HMAC 연산 비용은 nginx 성능에 영향을 줄 만큼 크지 않고(서브 밀리초), API 키처럼 고엔트로피 값에 HMAC을 쓰는 것도 "DB 유출만으로는 검증이 안 되게" 만드는 정당한 방어 심층 전략이에요. 다만 **HMAC 비밀 키를 DB와 분리 보관**하는 게 이 설계의 핵심 전제이고, 캐시를 쓴다면 **키 폐기가 즉시 반영되는지**가 실무에서 가장 자주 놓치는 함정이에요.
