# 전략 재조립(recomposition) 구조: 밴딧의 천장을 넘는 법

## 쉬운 설명

지금 봇들은 **10개짜리 메뉴판**을 들고 있어요. 상대한테 뭐가 제일 잘 먹히는지 여러 판 해보고, 제일 나은 걸 고릅니다. 그런데 **메뉴 10개가 전부 그 상대한테 지면?** 봇은 "그중 제일 덜 지는 것"을 골라서 **평생 똑같이 집니다.** 메뉴판에 새 요리를 추가할 줄 모르거든요.

말씀하신 구조는 **재료를 잘게 쪼개두고, 지면 LLM이 재료를 새로 조합해서 없던 요리를 만드는 것**입니다. 이게 맞습니다. 밴딧은 **고르는 기계**고, LLM은 **만드는 기계**예요. 둘은 경쟁 관계가 아니라 **위아래로 붙는** 관계입니다.

단, 어려운 게 하나 있어요. **"뭐가 잘못됐는지"를 알아야 다시 조합할 수 있습니다.** 게임이 끝나고 "졌다" 한 마디만 들으면, 어디를 고쳐야 할지 모릅니다. 이걸 푸는 게 이 설계의 진짜 관문입니다.

---

## 일반 설명

> **앞 답변 정정**: 제가 "봇 대 봇에서는 UCB1 밴딧이 이미 최적에 가깝다"고 한 것은 **고정된 arm 집합 내에서만** 참입니다. 질문하신 건 **arm 집합 자체를 생성**하는 구조이고, 이건 밴딧이 원리적으로 할 수 없는 일입니다. 제 4번 논거는 이 설계에는 적용되지 않습니다.

---

### 1. 문제의 정확한 형태 — 밴딧은 "덜 지는 쪽"으로 수렴한다

지적하신 **"한번 밀리면 똑같이 진다"** 는 은유가 아니라 밴딧의 수학적 성질 그대로입니다.

UCB1은 **고정된 arm 집합에서 기대 보상 최대인 arm으로 수렴**합니다. 문제는 *최대*가 *충분히 좋다*를 뜻하지 않는다는 것입니다.

```
상대 봇 X에 대한 내 빌드 10개의 실제 승률:
  build1: 5%   build2: 8%   build3: 3%   ...   build7: 20%   ...   build10: 4%

→ UCB1은 수십 판 만에 build7로 수렴
→ 그 후 수백 판을 build7로 두고, 80% 진다
→ 영원히
```

밴딧은 **"이 메뉴 전체가 X에게 부적합하다"는 결론을 내릴 수 없습니다.** 탐색 공간 밖의 개념이기 때문입니다. BASIL에 봇들의 상대별 승률이 공개되어 있는데, 여기서 **특정 상대에게만 승률이 극단적으로 낮은 조합(흔히 nemesis라 부르는 것)** 이 관찰되는 이유가 이것입니다. 저자가 손으로 새 빌드를 추가해주기 전까지 해소되지 않습니다.

**따라서 제안하신 구조의 핵심 가치는 정확히 이것입니다 — LLM은 arm을 *고르는* 게 아니라 *만드는* 역할이다.**

| | 하는 일 | 할 수 없는 일 |
|---|---|---|
| **UCB1 밴딧** | 주어진 N개 중 최적 선택, 통계적으로 최적 | **N+1번째를 만들어내기** |
| **LLM** | 프리미티브를 재조합해 없던 전략 생성 | 어느 게 실제로 나은지 통계적 판정 |

**둘은 대체재가 아니라 상하 계층입니다.** 올바른 구조는 "LLM이 arm 생성 → 밴딧이 arm 착취"이고, 새로 생성된 arm은 사전 증거가 0이라 **밴딧이 여전히 필요합니다.**

### 2. 이 설계의 선행 사례 — 이미 검증된 패턴이다

말씀하신 구조는 새로 발명하는 게 아니라 **이미 두 번 검증된 패턴**입니다.

#### 2.1 Voyager (Minecraft) — 스킬 라이브러리 패턴의 원전

앞 문서에서 언급한 Voyager가 정확히 이 구조입니다:

1. **성장형 스킬 라이브러리** — 실행 가능한 코드(JavaScript 함수)로 스킬을 저장. 성공한 코드가 라이브러리에 들어감.
2. **검색·주입** — 스킬은 자연어 설명의 **임베딩 벡터로 색인**되고, 새 과제가 오면 **가장 관련 높은 5개를 꺼내 프롬프트에 주입**.
3. **반복 프롬프팅** — 실패 시 **세 가지 피드백 채널**(환경 상태, 실행 에러, 자기검증용 별도 LLM 호출)을 받아 **최대 4라운드** 코드를 고쳐 씀.

논문이 스킬을 **"temporally extended, interpretable, and compositional"** 하다고 기술합니다. **조합 가능(compositional)** — 이게 "작은 단위로 쪼개서 재조립"의 정확한 요건입니다. 그 결과 고유 아이템 3.3배, 테크트리 도달 최대 15.3배 가속.

#### 2.2 StarEvolve (2025) — RTS판 구현

SC2Arena와 함께 나온 **StarEvolve**가 RTS에 이걸 이식한 것입니다:

- **Planner–Executor–Verifier 계층 구조** — 전략 계획과 전술 실행을 분리.
- **iterative self-correction** — 반복적 자기 교정.
- **고품질 게임플레이 데이터 선별 스코어링 후 파인튜닝** — 성공 사례를 모델에 되먹임.

즉 **"안 통하면 재조립"의 RTS 버전이 이미 존재하고 전략 계획에서 우수한 성능을 보고**했습니다. 질문하신 직관이 맞다는 독립적 증거입니다.

> 다시 한번, **브루드워 구현체만 없습니다.**

### 3. 그런데 진짜 어려운 건 재조립이 아니다 — 세 개의 관문

여기서부터가 설계의 실체입니다. "LLM이 재조합한다"는 아이디어는 쉽고, 아래 셋이 프로젝트의 성패를 가릅니다.

#### 3.1 **관문 1: 신용 할당 (credit assignment) — 가장 중요**

*"중간단위 전략이 안 통하면"* 에서 **"안 통했다"를 어떻게 알 것인가**가 핵심입니다.

브루드워 한 판의 자연스러운 보상 신호는 **15분 뒤에 나오는 1비트(승/패)** 뿐입니다. 이 신호만으로는:

```
졌다.
  → 빌드가 틀렸나?
  → 정찰 타이밍이 늦었나?
  → 9분 30초 교전을 하지 말았어야 했나?
  → 3번째 확장이 너무 빨랐나?
  → 알 수 없음
```

**어디를 고칠지 모르는 상태에서 재조립하면 LLM은 무작위로 아무 데나 고칩니다.** 그러면 학습이 아니라 난수 생성입니다. 기존 봇이 승/패 밴딧이라는 거친 신호에 머무는 이유도 이게 **유일하게 모호하지 않은 신호**이기 때문입니다.

**해법: 모든 중간 단위 전략이 자기 종료 조건(postcondition)을 들고 다녀야 합니다.**

브루드워는 다행히 중간 신호를 프레임 단위로 계산할 수 있습니다:

| 측정 가능한 중간 지표 | 의미 |
|---|---|
| 병력 가치 비(내 army value / 추정 적 army value) | 교전 우위 |
| 자원 채취율 (분당 미네랄/가스) | 경제 우위 |
| 맵 컨트롤 (관측된 영역 %, 확장 수) | 공간 우위 |
| 테크 도달 시각 vs 목표 시각 | 빌드 진행도 |
| 유닛 교환비 (kill value / loss value) | 컨트롤 효율 |

이걸로 각 전략에 **검증 가능한 계약**을 붙입니다:

```
전략: "안전한 3번째 확장"
  사전조건: 병력가치비 ≥ 0.9, 적 병력 위치 미상 아님
  목표:     9:30까지 3넥 가동 + 병력가치비 ≥ 0.8 유지
  실패판정: 9:30 시점 미달성, 또는 그 전에 병력가치비 < 0.5
  → 실패 시 이 전략만 재조립 대상
```

**이러면 1비트/15분이 수십 개의 국소 신호/판으로 바뀝니다.** Voyager가 "self-verification" 모듈을, StarEvolve가 "Verifier"를 명시적으로 둔 이유가 정확히 이것입니다. **이 계약 설계가 프로젝트에서 가장 많은 시간이 들어갈 부분이고, 여기가 무너지면 나머지는 무의미합니다.**

#### 3.2 **관문 2: 조합의 유효성 — LLM은 불가능한 계획을 태연히 내놓는다**

재조립한 결과가 **물리적으로 실행 불가능**할 수 있습니다. 자원이 모자라거나, 테크가 안 열렸거나, 타이밍이 산술적으로 불가능하거나.

**해법이 이미 존재합니다: BOSS (Build Order Search System).** Dave Churchill의 UAlbertaBot에 포함된 C++ 컴포넌트로, **"이 유닛/건물 집합을 원한다"고 주면 분기한정(branch-and-bound) 탐색으로 근최적 빌드 오더를 찾아줍니다** (적 간섭 없다고 가정).

이걸 쓰면 역할 분담이 깔끔해집니다:

```
LLM 출력  (선언적 목표):
  { "목표": "9:30까지 럴커 2 + 히드라 6",
    "제약": "앞마당 유지, 드론 30 이상" }
         ↓
BOSS (결정론적 솔버):
  실행 가능한 빌드 오더로 컴파일. 불가능하면 거부.
         ↓
FSM (실행):
  프레임 단위 실행
```

**LLM은 빌드 오더를 직접 뱉지 않습니다.** 목표만 말하고, 조합 폭발과 실현가능성 검사는 **이미 존재하는 솔버**가 합니다. LLM 출력 공간이 작고 선언적이 되므로 환각 여지도 줄고 검증도 쉽습니다.

교전 쪽도 같은 패턴입니다 — LLM이 "이 교전은 피해라"라고 하면 **SparCraft/FAP 전투 시뮬레이터**가 실제 손익을 계산해 거부권을 행사합니다.

> **일반 패턴: LLM이 제안하고, 기호적 솔버가 기각한다 (LLM proposes, symbolic solver disposes).** RTS는 이 패턴을 쓰기에 이례적으로 좋은 도메인입니다 — 검증기가 이미 오픈소스로 다 있습니다.

#### 3.3 **관문 3: 프리미티브 입도(granularity) — 설계의 진짜 분기점**

*"행동을 더 작게 쪼개서"* 에서 **얼마나 작게**가 성패를 가릅니다.

| 입도 | 결과 |
|---|---|
| **너무 굵음** — "4게이트 러시", "패스트 캐리어" | 빌드 선택으로 회귀. **밴딧이 더 낫다.** 조합의 자유도가 없음 |
| **적정** — 10~60초 단위 **선언적 의도** | ✅ LLM 레이턴시 예산과 자연스럽게 맞음 |
| **너무 잘음** — 유닛별 명령 | 조합 공간 폭발, 레이턴시 파탄, 그리고 이건 **FSM이 이미 더 잘함** |

브루드워에서 적정 구간은 대략 이런 형태입니다 (전부 **파라미터를 갖고**, **조건부로 묶임**):

```
확장(위치, 시점, 방어하한)
정찰(경로, 시점, 목표정보)
병력구성(유닛비, 시한, 총가치)
진영유지(지점, 최소병력, 해제조건)
견제(목표, 유닛, 시점, 철수조건)
테크(목표, 방어하한, 포기조건)
교전정책(교전비 임계값, 후퇴선)
```

핵심은 **파라미터와 조건부 결합**입니다. 앞 문서에서 든 예를 다시 보면:

```
나쁨:  "4게이트"
       → 빌드 테이블의 한 줄. 밴딧이 표현 가능. LLM 불필요.

좋음:  진영유지(입구, 럴커2, 해제=뮤탈관측)
       + 확장(3시, 9:30, 방어하한=0.8)
       + 테크(하이브, 포기조건=병력가치비<0.6)
       → 3개 프리미티브의 파라미터화된 조합.
         테이블로 열거 불가. 여기서 LLM이 값을 한다.
```

**표현력 테스트**: 새로 만든 전략이 기존 빌드 테이블의 한 줄로 쓸 수 있으면, 그건 LLM이 필요 없는 것입니다.

### 4. 그래서 "이길 수 있는 상태"가 되는가

**필요조건으로는 맞습니다. 충분조건은 아닙니다.**

- **필요조건인 이유**: arm 생성 없이는 1절의 천장을 원리적으로 못 넘습니다. 이 계층이 없으면 최선이 "사람이 손으로 빌드를 계속 추가해주는 봇"입니다.
- **충분조건이 아닌 이유**: 3절의 세 관문이 전부 동작해야 하고, 그 위에 아래 두 가지가 더 남습니다.

#### 4.1 표본 효율 — 새 전략은 증거가 0이다

새로 조합한 전략은 **사전 승률 정보가 없습니다.** 55% 전략과 45% 전략을 통계적으로 구분하려면 수백 판이 필요합니다. 따라서:

- **재조립은 매 판 하면 안 됩니다.** "밀리고 있음"이 통계적으로 확립됐을 때만 트리거해야 합니다 (예: 특정 상대 최근 30판 승률 < 25%).
- 생성된 arm은 **밴딧 arm 집합에 추가**되어 정상적으로 탐색/착취 대상이 됩니다. 즉 **LLM은 밴딧을 대체하지 않고 밴딧에 먹이를 줍니다.**
- BASIL은 최근 100판 승률 15% 미만이면 봇을 자동 비활성화하므로, **탐색 비용이 래더 순위로 직접 청구됩니다.** 무분별한 생성은 봇을 죽입니다.

#### 4.2 솔직한 반론 — 전문가가 이미 상당 부분 열거해뒀다

PurpleWave는 관측·소거법으로 적 전략을 판정하고 **수백 개의 하드코딩된 반응**을 갖고 있습니다. 즉 **유용한 조합 공간의 상당 부분을 이미 사람이 손으로 채워놨습니다.** LLM이 생성한 조합이 **전문가가 열거한 조합을 이겨야** 의미가 있는데, 봇 상대로는 쉽지 않습니다.

**다만 이 반론에 정확히 걸리지 않는 표적이 하나 있습니다 — nemesis 문제입니다.**

- 정의: 특정 상대에게만 승률이 극단적으로 낮은 조합. 손코딩 반응이 커버 못 했고, 밴딧이 탈출 못 하는 케이스.
- **BASIL은 상대별 승률을 공개합니다.** 즉 표적이 사전에 식별 가능하고, 개선이 객관적으로 측정됩니다.
- 그리고 이건 **재조립 외에는 해결 수단이 없는 문제**입니다 (사람이 손으로 고치는 것 제외).

**→ 이게 봇 대 봇 무대에서도 성립하는 구체적 평가 지표입니다.** 앞 답변에서 "봇 대 봇에선 이득 없다"고 한 것의 예외이고, 실제로 이 프로젝트의 1순위 벤치마크로 삼을 만합니다:

> **"재조립 계층을 켰을 때, nemesis 상대 승률이 유의하게 오르는가. 그리고 나머지 상대 승률을 깎아먹지 않는가."**

---

### 5. 정리된 아키텍처

```
┌─────────────────────────────────────────────────────┐
│ 재조립 계층 (LLM, 비동기, 드물게 호출)                  │
│  트리거: 특정 상대 승률 < 임계, 또는 전략 계약 반복 실패   │
│  입력:   실패한 전략의 계약 + 위반된 지표 + 관측 요약      │
│  출력:   프리미티브의 새 파라미터화 조합 (선언적 목표)      │
└──────────────────────┬──────────────────────────────┘
                       │ 새 arm 추가
┌──────────────────────▼──────────────────────────────┐
│ 선택 계층 (UCB1 밴딧, 게임 간 영속)                     │
│  상대별 전적으로 arm 선택. 생성된 arm도 동등하게 취급      │
│  저장: bwapi-data/write → read (100MB)               │
└──────────────────────┬──────────────────────────────┘
                       │ 선택된 전략 (선언적 목표)
┌──────────────────────▼──────────────────────────────┐
│ 검증/컴파일 계층 (결정론적 솔버) — 기존 오픈소스 활용      │
│  BOSS: 목표 유닛 집합 → 실현가능 빌드 오더 (branch&bound)│
│  SparCraft/FAP: 교전 손익 시뮬레이션 → 교전 거부권        │
│  실현 불가능한 LLM 출력은 여기서 차단                    │
└──────────────────────┬──────────────────────────────┘
                       │ 실행 가능한 계획
┌──────────────────────▼──────────────────────────────┐
│ 실행 계층 (FSM, 프레임 단위)                           │
│  전투/생산/유닛 제어. 프레임 예산 준수                   │
│  + 계약 감시기: 병력가치비/채취율/맵컨트롤 상시 측정       │
│    → 계약 위반 시 재조립 계층에 신호 (신용 할당의 근거)    │
└─────────────────────────────────────────────────────┘
```

핵심 흐름 세 줄:

1. **FSM이 실시간을 흡수하고, 계약 감시기가 "어디가 깨졌는지"를 국소화한다.**
2. **LLM은 깨진 부분만 재조립해 새 arm을 만든다. 빌드 오더가 아니라 선언적 목표를 낸다.**
3. **기존 솔버(BOSS/SparCraft)가 실현가능성을 검증하고, 밴딧이 통계적으로 판정한다.**

이 구조에서 LLM은 **전체 의사결정의 매우 작은 부분**만 담당합니다. 그게 맞습니다 — 앞 문서들에서 확인한 대로 LLM의 강점은 매크로 판단이지 실행이 아니고, 나머지는 이미 20년간 최적화된 컴포넌트들이 훨씬 잘합니다.

---

### 6. 구현 순서 제안

| 단계 | 내용 | 검증 기준 |
|---|---|---|
| 1 | 기존 오픈소스 봇 하나 선정, 빌드/재생 가능하게 (PurpleWave는 Scala, UAlbertaBot은 C++ + BOSS 포함) | BASIL/SSCAIT에서 베이스라인 Elo 확보 |
| 2 | **계약 감시기** 구현 — 병력가치비/채취율/맵컨트롤 프레임 단위 측정 + 로깅 | 지표만 보고 패배 원인을 사람이 짚을 수 있는가 |
| 3 | 프리미티브 DSL 정의 + 기존 빌드를 전부 DSL로 재표현 | 기존 빌드가 DSL로 손실 없이 표현되는가 |
| 4 | 상태 직렬화 (BWAPI → 텍스트). 컨텍스트 압축 필요 | 프롬프트 토큰 수가 예산 내인가 |
| 5 | LLM 재조립 계층 (오프라인, 수동 트리거부터) | 생성물이 BOSS 검증을 통과하는 비율 |
| 6 | 밴딧에 생성 arm 편입 + 자동 트리거 | **nemesis 상대 승률 개선, 나머지 승률 비회귀** |
| 7 | (대회 출전 시) 오프라인 증류 — LLM 결정을 테이블/소형 모델로 압축해 100MB read에 탑재 | BASIL 네트워크 금지 규칙 준수 |

2단계가 가장 지루하고 가장 중요합니다. **3.1의 신용 할당이 이 프로젝트의 진짜 난이도**입니다.
