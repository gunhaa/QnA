# 봇+LLM으로 사람과 직접 래더를 두는 구조 — 무대 선택부터 아키텍처까지

## 쉬운 설명

사람이랑 직접 두게 하는 건 **가능합니다. 단, 정해진 놀이터가 있어요.**

**SCHNAIL**이라는 곳은 "사람 대 봇"을 하라고 만든 데예요. 사람들이 **봇인 줄 알고 들어옵니다.** 등수도 매겨줍니다. 여기는 환영받아요.

반대로 **iCCup이나 공식 배틀넷**은 안 됩니다. 규칙에 "남보다 유리해지는 프로그램 금지"라고 적혀 있고 걸리면 계정이 날아갑니다. 게다가 거기 있는 사람들은 **사람이랑 두는 줄 알고** 들어온 거예요.

그리고 재밌는 게 하나 있어요. **사람이랑 둘 때는 오히려 LLM 쓰기가 훨씬 편해집니다.** 봇끼리는 게임을 빨리감기로 돌려서 시간이 없는데, 사람이랑은 한 판에 15분씩 걸리거든요. 심지어 **게임 시작 전이랑 끝난 후엔 시간이 무제한**이에요. 거기서 제일 중요한 생각을 하면 됩니다.

## 일반 설명

### 1. 무대 선택 — 여기서 먼저 갈린다

| 무대 | 가능? | 근거 |
|---|---|---|
| **SCHNAIL** (StarCraft Human 'N' AI League) | ✅ **이걸 위해 만들어진 곳** | 인간 vs 봇 전용 런처. 인간·봇 공용 Elo 랭크(1500 시작, K=32). 봇 저자가 직접 제출, "practice only" 옵션도 제공. Artosis가 여기 경기를 중계한 전례 있음 |
| **DropLauncher** | ✅ | BWAPI 봇을 로컬에서 인간 vs 봇으로 붙여주는 런처. 자체 실험/쇼매치용 |
| **iCCup** | ❌ | **규칙상 명시적 금지** — "다른 플레이어보다 유리하게 하는 모든 프로그램 사용 금지". 처벌은 **계정 밴 또는 clearstats** |
| **공식 Battle.net (Remastered) / Fish 서버** | ❌ | Blizzard가 서드파티 핵으로 **35만+ 계정 폐쇄**. 게다가 **기술적으로도 불가** — BWAPI 4.4는 **StarCraft 1.16.1만 지원**, Remastered 미지원 |

인가된 무대와 아닌 무대의 차이는 규칙만이 아닙니다. **SCHNAIL의 인간 상대는 봇과 둔다는 걸 알고 동의하고 들어옵니다.** iCCup·배틀넷 상대는 사람과 둔다고 믿고 들어온 사람들이라, 거기 봇을 올리는 건 규칙 위반인 동시에 상대를 속이는 일이 됩니다.

**다행히 이건 제약이 아닙니다 — SCHNAIL이 정확히 원하시는 것을 제공합니다.** 실제 인간 상대, 공식 Elo, 반복 대전, 공개 리더보드. 필요한 게 다 있습니다.

> ⚠️ SCHNAIL의 2026년 현재 활성도는 확인하지 못했습니다(자료가 2019~2022년에 집중). 착수 전에 런처 동작 여부와 현재 인구를 직접 확인하세요. 만약 유휴 상태라면 DropLauncher 기반 자체 쇼매치가 대안입니다.

### 2. 상대가 사람으로 바뀌면 설계가 뒤집힌다

이게 이 질문의 진짜 내용입니다. 봇 대 봇에서 옳았던 것이 **대부분 반대가 됩니다.**

#### 2.1 밴딧이 역전된다 — 수렴이 곧 약점이 된다

| | 봇 대 봇 | **인간 대 봇** |
|---|---|---|
| 상대 성질 | **정상(stationary)** — 고정 바이너리 | **비정상(non-stationary)** — 적응함 |
| 밴딧의 수렴 | **자산**. 최적 카운터 고정 | **부채**. 고정된 순간 읽히고 착취당함 |
| 결정론적 정책 | 최적 | **착취 가능(exploitable)** |
| 필요한 것 | 빠른 수렴 | **끝나지 않는 탐색 + 전략 분포(혼합 전략)** |

앞 문서에서 확인한 관찰 — *"인간은 1~2판만 겪으면 봇의 작은 실수를 찾아내 다전제를 쓸어간다"* — 이 현상의 정확한 원인이 이것입니다. 봇의 수렴한 정책은 **결정론적이라 착취 가능**합니다.

**따라서 arm 집합이 계속 커져야 합니다.** 앞 문서의 재조립 계층이 봇 대 봇에서는 "있으면 좋은 것"이었지만, **인간 상대에서는 구조적 필수**가 됩니다. 이 무대로 옮기는 순간 LLM 계층의 정당화가 훨씬 쉬워집니다.

#### 2.2 표본이 100배 귀해진다 — 그리고 그게 LLM의 존재 이유가 된다

| | 봇 대 봇 | 인간 대 봇 |
|---|---|---|
| 판당 소요 | BASIL 최고속 병렬 | **실시간 10~20분** |
| 확보 가능 판수 | AIIDE 2만 판 / BASIL 24시간 연속 | **하루 몇 판 ~ 수십 판** |
| 동일 상대 반복 | 수백 판 | **운 좋아야 10~20판** |

**결과: 상대별 밴딧 통계가 성립하지 않습니다.** 한 사람과 100판을 둘 수 없으니까요.

그런데 이게 **LLM을 정당화하는 가장 강한 논거**입니다. 통계를 못 쌓는 상황에서 필요한 건 **1~2판 관측에서 일반화하는 능력**이고, 그게 정확히 few-shot 추론입니다. 밴딧이 못 하는 일이죠.

추가로 **사람 간 전이**가 필요합니다. 개인별 표본이 부족하니 유형 단위로 묶어야 합니다:

```
개인별 통계 (불가능):     "player_A는 내 럴커 전략에 12판 중 9판 승"
유형 기반 추론 (가능):     "player_A는 초반 압박 후 앞마당 늦게 가는 부류.
                          같은 부류였던 player_C/F에게 통했던 대응은 ..."
```

#### 2.3 레이턴시 압박이 실제로 풀린다 — 그리고 핵심 통찰 하나

인간전은 **정상 속도 실시간**입니다. 판당 10~20분, 전략 판단 주기를 30~60초로 잡으면 LLM 왕복이 넉넉히 들어갑니다.

**그런데 더 중요한 건 이것입니다 — LLM 호출 지점 3개 중 2개는 레이턴시 압박이 0입니다.**

| 호출 지점 | 시간 압박 | 하는 일 | 가치 |
|---|---|---|---|
| **게임 전 브리핑** | **없음 (무제한)** | 상대 프로필 + 맵 + 종족 매치업 → 오프닝 정책과 분기 트리 설정 | ⭐ **최고** |
| 게임 중 재조립 | 있음 (비동기 스레드) | 계약 위반 시 해당 전략만 재조립 | 중 |
| **게임 후 AAR** | **없음 (무제한)** | 구조화된 복기를 상대 프로필에 기록 | ⭐ **최고** |

> **가장 가치 높은 LLM 호출이 게임 밖에 있습니다.** 이게 이 설계의 핵심입니다. 실시간 RTS에 LLM을 넣는 문제를 "실시간에 넣지 않는 것"으로 상당 부분 우회할 수 있습니다. 게임 중 호출은 보조이고, 무거운 추론은 전부 게임 전후로 밀어냅니다.

#### 2.4 상대 모델이 "프로그램"에서 "사람"으로 바뀐다

- 사람은 **습관, 선호 빌드, 특정 상황의 버릇, 기울기(tilt)** 를 갖습니다. 프로그램보다 훨씬 풍부한 모델링 대상이고, 자연어로 기술하기에 딱 맞습니다 — LLM의 영역입니다.
- 그리고 **상대도 나를 학습합니다.** 양방향 적응이 일어나는 반복 게임입니다.
- 앞 문서의 연구 분포(Minecraft·Pokémon 중심)를 보면, **실시간 환경에서 인간과 양방향 적응을 벌이는 LLM 에이전트는 거의 연구된 적이 없습니다.** 이 프로젝트의 진짜 차별점이 여기 있습니다.

### 3. 배포 문제 — 반드시 먼저 풀어야 할 실무 관문

**SCHNAIL은 봇을 플레이어의 로컬 PC로 다운로드해 실행합니다** (SSCAIT 활성 봇 전체가 747MB). 즉 **당신 봇이 낯선 사람 PC에서 돌아갑니다.**

| 옵션 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 프록시 서버** | 봇 → 당신 서버 → LLM | API 키 보호, 모델 교체 자유, **모든 대전 로그 중앙 수집** | 비용 전액 부담, 남용 가능(레이트리밋·인증 필수), 서버 다운 = 봇 다운 |
| B. 로컬 소형 모델 동봉 | 봇에 모델 포함 | 네트워크 불필요 | 스타1과 동시 구동 부담, 배포 용량 수 GB |
| C. 오프라인 증류 | 런타임 LLM 0 | 배포 단순, BASIL 규칙도 통과 | **2.1의 "계속 커지는 arm" 이점을 잃음** — 인간전의 핵심 가치가 사라짐 |
| **D. 자체 호스팅 쇼매치** | DropLauncher로 직접 상대 모집 | 통제력 최대, 크래시 대응 즉시 | 표본 최소, 사람 섭외 필요 |

**추천: D → A 순서.** 초기엔 D로 지인·커뮤니티·스트리머 상대로 반복 실험하며 안정화하고(여기서 크래시와 명백한 버그를 다 잡고), 검증되면 A로 SCHNAIL에 배포합니다.

C는 매력적으로 보이지만 **인간전에서는 자충수**입니다. 증류한 정책은 다시 결정론적이 되고, 2.1의 착취 문제로 되돌아갑니다. C는 대회(BASIL) 출전용 별도 트랙으로만 쓰세요.

### 4. 실제로 얼마나 세질 수 있나 — 솔직한 상한

**올릴 수 있는 것과 없는 것을 분리해야 합니다.**

현재 브루드워 봇은 ICCup **D ~ C-** 수준입니다. 여기서 C+/B로 올라가는 격차의 대부분은 **마이크로와 멀티태스킹 실행**이고, **LLM은 여기에 기여하지 않습니다.** 그건 손코딩이나 RL의 영역이고 이 프로젝트와 직교합니다.

**그런데 봇이 인간에게 지는 *방식*은 다릅니다:**

```
1판째:  봇이 이기거나 대등        ← 봇의 소재 자체는 C- 상대에 충분
2판째:  인간이 구멍을 하나 찾음
3판째~: 같은 구멍으로 계속 짐      ← 여기서 무너진다
```

**LLM 재조립이 겨냥하는 건 정확히 3번째 줄입니다.** 그래서 현실적 목표는:

> **피크 실력을 올리는 게 아니라, "착취당해 무너지는 것"을 제거하는 것.**
>
> *"C- 상대로 1판은 이기지만 3판째부터 전패"* → *"C- 상대로 20판 다전제에서 40~50% 유지"*

이건 작아 보이지만 **기존 봇 전체가 못 하는 일**이고, 20년간 이 분야의 알려진 고질병입니다. 그리고 **측정이 깨끗합니다.**

### 5. 평가 설계 — 실험 하나로 끝난다

SCHNAIL은 인간·봇 공용 Elo를 제공합니다. 핵심 실험은 이것 하나입니다:

> **같은 인간 상대에 대한 "누적 판수 vs 승률" 곡선**
>
> - 재조립 **OFF**: 판수가 늘수록 승률 **하락** (인간이 학습해서 착취)
> - 재조립 **ON**: **평탄 또는 상승**

이 곡선 하나가 프로젝트 전부가 될 수 있습니다. 강력한 이유:

1. **기존 봇은 전부 하락 곡선이라는 게 이미 알려져 있습니다** — 앞 문서의 "다전제에서 인간이 쓸어간다"는 관찰이 곧 베이스라인입니다.
2. **A/B가 깨끗합니다** — 같은 봇, 재조립 계층만 on/off.
3. **표본이 적어도 신호가 큽니다** — 전패 → 40%는 20판이면 보입니다.
4. **LLM 게임 에이전트 논문 대부분이 "내장 AI 상대 승률"이라는 약한 평가에 머무는 것과 대비됩니다.**

보조 지표: SCHNAIL Elo 절대값, 상대가 같은 전략을 반복 사용한 비율, 계약 위반 유형별 빈도.

### 6. 인간전 특화 아키텍처

```
━━━━━━━━━━ 게임 전 (시간 무제한) ━━━━━━━━━━
  입력:  상대 프로필(과거 AAR 누적) + 맵 + 매치업
  LLM:   오프닝 정책 + 분기 트리 + 각 분기의 계약(postcondition) 설정
  출력:  이번 판의 전략 계획 → BOSS로 빌드 오더 컴파일
                    │
━━━━━━━━━━ 게임 중 (실시간) ━━━━━━━━━━━━━━
  ┌─────────────────▼──────────────────────┐
  │ FSM 실행 계층 (프레임 단위)               │
  │  전투·생산·유닛 제어                      │
  │  + 계약 감시기: 병력가치비/채취율/맵컨트롤  │
  └─────────────────┬──────────────────────┘
                    │ 계약 위반 감지
  ┌─────────────────▼──────────────────────┐
  │ 재조립 (비동기 스레드, 30~60초 주기)       │
  │  깨진 전략만 프리미티브 재조합             │
  │  → BOSS/SparCraft가 실현가능성 검증        │
  │  ※ 프레임 루프는 직전 계획으로 계속 진행    │
  └─────────────────┬──────────────────────┘
                    │
━━━━━━━━━━ 게임 후 (시간 무제한) ━━━━━━━━━━
  입력:  리플레이 + 계약 위반 로그 + 최종 결과
  LLM:   구조화된 복기(AAR) 작성
         "이 사람은 ~할 때 ~한다. 다음엔 ~를 대비"
  출력:  상대 프로필 갱신 + 새 arm을 밴딧 집합에 추가
                    └──────→ 다음 게임 전 브리핑으로
```

**핵심: 무거운 추론은 전부 게임 밖에 있고, 게임 중 LLM은 보조 역할만 합니다.**

### 7. 실무 주의사항

1. **안정성이 실험 가능성의 전제입니다.** 사람의 시간을 쓰는 실험이라, 봇이 자주 크래시하거나 눈에 띄게 느리면 아무도 상대해주지 않습니다. 프록시 서버가 죽었을 때 **LLM 없이도 정상 플레이하는 폴백**이 반드시 있어야 합니다.

2. **리플레이를 전부 저장하세요.** 표본이 100배 귀하므로 한 판도 버리면 안 됩니다. 프록시 서버(옵션 A)를 쓰면 로그가 중앙에 모이는 부수 효과가 있습니다.

3. **"LLM을 쓴다"고 밝히는 게 유리합니다.** SCHNAIL 이용자는 어차피 봇인 줄 알고 들어오고, LLM 봇이라는 점은 오히려 **사람을 끌어모으는 요인**입니다. Artosis가 SCHNAIL 경기를 중계한 전례가 있으니 홍보 경로도 있습니다. 표본 확보가 이 프로젝트의 최대 제약이므로 이건 실질적 이점입니다.

4. **비용 상한을 걸어두세요.** 프록시 방식은 남이 게임할 때마다 당신이 돈을 냅니다. 봇당/일일 호출 상한과 인증이 필요합니다.

5. **BWAPI 버전 제약을 미리 확인하세요.** BWAPI 4.4 + StarCraft **1.16.1**입니다. Remastered가 아닙니다. 개발 환경 구성 시 첫 관문입니다.

### 8. 정리

| 질문 | 답 |
|---|---|
| 사람과 직접 래더 가능? | **SCHNAIL에서 가능하고, 그게 유일한 인가된 무대.** iCCup·배틀넷은 규칙 위반이고 BWAPI가 Remastered를 지원하지도 않음 |
| 봇 대 봇보다 나은가? | **LLM 관점에서는 훨씬 낫다.** 밴딧이 무력해지고(상대가 적응), 표본이 귀해지고(few-shot 필요), 레이턴시가 풀린다(정상 속도 + 게임 전후 무제한) |
| 가장 큰 설계 통찰 | **가치 높은 LLM 호출 2개(사전 브리핑, 사후 AAR)가 레이턴시 압박이 0인 지점에 있다** |
| 가장 큰 실무 관문 | **배포** — 봇이 남의 PC에서 도므로 프록시 서버 필요. 그리고 **표본 확보** |
| 현실적 성능 목표 | 피크 실력 상승이 아니라 **다전제 착취 내성**. "3판째부터 전패" → "20판 다전제 40~50%" |
| 평가 | **동일 인간 상대 누적판수 vs 승률 곡선**, 재조립 on/off A/B |
