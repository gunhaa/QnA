# FSM(전투·생산) + LLM 오케스트레이터(전략) 구조는 왜 스타1 봇에 없는가

## 쉬운 설명

사실 그 구조는 **이미 있어요.** 연구자들도 똑같이 생각했고, 똑같이 만들었어요. 다만 **스타크래프트 2에서** 만들었습니다. 빠른 손놀림은 미리 짜둔 기계가 하고, 큰 작전은 가끔 LLM한테 물어보는 — 정확히 그 구조예요.

그럼 스타1(브루드워)에는 왜 없냐? 이유는 "나쁜 아이디어라서"가 아니라 훨씬 시시합니다.

1. **대회장이 인터넷을 막아놨어요.** 봇들이 겨루는 래더는 인터넷 접속이 규칙상 금지입니다. API를 못 부르니 애초에 출전이 안 돼요.
2. **번역기가 없어요.** 스타2는 게임 상황을 글로 바꿔주는 도구가 이미 공짜로 있는데, 스타1은 아무도 안 만들어놨어요. 직접 만들어야 하는데 몇 달짜리 잡일입니다.
3. **사람들이 안 겹쳐요.** 스타1 봇 만드는 사람은 20년 된 C++ 취미 개발자, LLM 에이전트 만드는 사람은 논문 쓰는 파이썬 연구자. 서로 남의 동네에 안 갑니다.

---

## 일반 설명

> 앞 문서에서 제가 든 "레이턴시" 논거는 **LLM을 프레임 루프 안에 넣는 경우**에만 해당합니다. 질문하신 **비동기 오케스트레이터** 구조 — FSM이 실시간을 흡수하고 LLM은 전략 전이에서만 호출 — 에는 적용되지 않습니다. 실제 이유는 따로 있습니다.

---

### 1. 전제 정정: 그 구조는 존재한다. LLM-RTS 연구의 **표준 설계**다

질문하신 구조는 이 분야에서 이미 수렴한 정답입니다. 대표적으로 **SwarmBrain**(arXiv 2401.17749)이 문자 그대로 그 설계입니다.

| SwarmBrain 구성 요소 | 역할 | 질문하신 구조와의 대응 |
|---|---|---|
| **Overmind Intelligence Matrix** (LLM 구동) | 저그 "전체 의식"을 모사 — 자원 배분, 확장 방향 결정, 다면 공격 조율 | **LLM 오케스트레이터 = 전략 수정** |
| **Swarm ReflexNet** | **condition-response state machine** 프레임워크. 기본 유닛 기동의 즉각적 전술 반응 | **FSM = 전투/생산 소규모 판단** |

논문이 ReflexNet을 둔 이유를 명시적으로 이렇게 씁니다 — *"LLM 추론에 내재된 레이턴시 때문에(due to the inherent latency in LLM reasoning)"*. **당신이 도달한 결론과 동일한 추론 경로**입니다. 성능은 내장 AI 기준 하위 난이도 100% 승률, Hard 76%.

Overmind Intelligence Matrix 자체도 **Overmind Brain + SC2 Brain** 2단으로 쪼개져 있습니다. 즉 오케스트레이터 안에서도 "무엇을 할지"와 "SC2 문법으로 어떻게 표현할지"를 분리했습니다.

같은 계열이 더 있습니다:

- **TextStarCraft2 / Chain of Summarization** (NeurIPS 2024) — 관측을 단일 프레임 요약 → 다중 프레임 요약으로 압축해 LLM에 넘기고, 실행은 스크립트. 내장 AI Harder(Lv5) 격파.
- **LLM-PySC2** (2024) — LLM 에이전트용 SC2 환경 표준화.
- **SC2Arena / StarEvolve** (2025) — 벤치마크 + 자기개선 프레임워크.
- **Hierarchical Expert Prompt** (2025) — 내장 Elite(Lv7) 최초 격파.

**결론: "왜 없냐"의 답은 "있다"입니다. 없는 건 이 구조 자체가 아니라, 이 구조의 브루드워 구현체입니다.**

### 2. 그럼 왜 브루드워 대회에는 없는가 — 규칙이 구조적으로 배제한다

이게 가장 직접적이고, 가장 시시한 이유입니다.

#### 2.1 BASIL 래더: **인터넷 접속 명시적 금지**

브루드워 봇의 주 무대인 **BASIL**(24/7 상시 래더, Docker + Wine 기반)의 규칙:

- **"Accessing the internet/network is generally prohibited."**
- 봇은 read + write + ai 디렉터리 합쳐 **총 100MB** 디스크.
- 크래시는 패배 처리. 6시간마다 봇 자동 업데이트.

API 호출 봇은 **규칙 위반이라 출전 자체가 불가능**합니다.

#### 2.2 SSCAIT: 샌드박스 환경

- 실행 환경: **32비트 Windows 7 머신**.
- 파일 I/O: `bwapi-data/read/`(읽기, 100MB 제한) + `bwapi-data/write/`(쓰기)만 허용. **그 외 디렉터리 읽기/쓰기 금지.**
- 프레임 예산: **1프레임 10초 초과 / 10프레임 1초 초과 / 320프레임 85ms 초과 시 패배.**
- 제출 형태: C++ BWAPI AI Module(DLL), Proxy Bot(EXE), 또는 Java(JAR).

여기서 주목할 점 — **프레임 예산은 비동기 스레드로 우회 가능합니다.** 별도 스레드에서 LLM을 호출하고 메인 루프는 직전 전략으로 계속 돌면 85ms 규칙에 안 걸립니다. 즉 **기술적 장애물은 프레임 예산이 아니라 샌드박스 환경**입니다.

#### 2.3 AIIDE: 전체 소스 공개 의무 + 조직위 빌드

- **전체 소스 코드 제출 의무.** 누락/난독화 시 실격. 실제로 BigEyes는 결과 발표 후 소스 미제출로 실격 처리됨.
- 봇은 **공식 BWAPI 릴리스로 조직위 환경에서 컴파일·실행**되어야 함.
- 대회 후 소스·바이너리·전체 경기 결과를 공개 — **재현성이 명시적 설계 목표.**

API 키가 필요하고, 외부 서비스에 의존하고, 모델 버전이 바뀌면 행동이 달라지는 봇은 **이 재현성 요구와 근본적으로 충돌**합니다.

#### 2.4 경기 물량의 경제학

- AIIDE는 라운드로빈 반복. 2015년 VM 전환 후 2주간 **20,788 경기**.
- BASIL은 **최대 속도로 병렬 다중 경기를 24시간 돌립니다.**

게임당 LLM 호출이 수십 회라면 대회 한 번에 수십만~수백만 호출입니다. **취미 개발자가 감당할 비용이 아니고**, 조직위가 대신 내줄 이유도 없습니다.

> **정리: 브루드워 대회 생태계는 "오프라인·결정론적·자체완결 바이너리"를 전제로 20년간 굳어졌습니다. LLM 오케스트레이터는 이 전제를 전부 위반합니다. 누군가 검토하고 기각한 게 아니라, 애초에 출전할 무대가 없습니다.**

### 3. 대회 밖에서도 왜 없는가 — 더 근본적인 이유

대회를 포기하고 개인 프로젝트로 하면 되지 않냐? 그런데도 (찾을 수 있는 범위에서는) 없습니다. 이유는 네 가지입니다.

#### 3.1 **언어 래퍼가 없다 — 이게 진짜 장벽입니다**

| | StarCraft II | StarCraft: Brood War |
|---|---|---|
| 공식 API | Blizzard 공식 지원, **PySC2**(Python) | 없음. **BWAPI**(커뮤니티, C++ DLL 인젝션) |
| 언어 환경 래퍼 | TextStarCraft2, LLM-PySC2, SC2Arena — **기성품** | **없음. 직접 만들어야 함** |
| 실행 환경 | 네이티브 리눅스 헤드리스 | 32비트 Windows / Wine + Docker |
| LLM 생태계 접근성 | Python 네이티브 | C++/Java ↔ Python IPC 브리지 필요 |

LLM 오케스트레이터에서 **실제 작업량의 대부분은 LLM 호출이 아니라**:
1. **상태 직렬화** — BWAPI 게임 상태 중 무엇을 어떤 형식의 텍스트로 뽑을 것인가
2. **액션 문법** — LLM 출력을 FSM이 실행 가능한 지시로 바인딩하는 스키마
3. **컨텍스트 압축** — 매 호출마다 수백 유닛/건물 상태를 어떻게 줄일 것인가

TextStarCraft2의 Chain of Summarization이 존재하는 이유가 정확히 3번입니다. **원시 관측이 컨텍스트에 안 들어가서** 단일 프레임 요약 + 다중 프레임 요약 2단 압축을 발명해야 했습니다. SC2 연구자는 이걸 **공짜로 물려받고**, 브루드워 개발자는 **처음부터 만들어야 합니다.**

#### 3.2 **두 커뮤니티가 겹치지 않는다**

| | BWAPI 봇 개발자 | LLM 에이전트 연구자 |
|---|---|---|
| 규모 | 수십 명, 취미/학생 | 수백~수천 명, 학계/산업 |
| 언어 | C++, Java, Scala | Python |
| 코드베이스 | 10년+ 누적, 수만 줄 | 논문 단위 신규 |
| 동기 | 래더 Elo, 커뮤니티 | 논문 게재, 벤치마크 SOTA |
| 환경 선택 기준 | 스타1을 좋아해서 | **기성 벤치마크가 있는 곳** |

A그룹은 파이썬 LLM 배관 작업을 할 이유가 없고, B그룹은 1998년 게임의 DLL 인젝션을 Wine에서 디버깅할 이유가 없습니다. **교집합이 사실상 비어 있습니다.**

#### 3.3 **논문 신규성이 이미 소진됐다**

2026년에 "브루드워에 LLM 오케스트레이터 + FSM" 논문을 내면 리뷰어 반응은 **"SwarmBrain이 2024년에 했다"** 입니다. 아키텍처는 더 이상 새롭지 않고, 새로운 건 환경뿐인데 — ML 커뮤니티 시각에서 브루드워는 **SC2보다 도구가 부실하고 덜 관련 있는 구버전**입니다. 학계 인센티브가 정확히 반대로 걸려 있습니다.

#### 3.4 **봇 대 봇에서는 LLM이 이길 여지가 없다**

이게 설계상 가장 중요한 지점입니다.

대회 상대 봇은 **행동이 거의 결정론적**입니다. 이 상대에 대해서는 **UCB1 밴딧으로 10개 빌드 중 고르기**가 이미 최적에 가깝습니다 — 몇 판이면 수렴하고, 비용 0, 분산 0, 레이턴시 0. BananaBrain이 정확히 이걸 합니다.

**LLM의 우위는 "처음 보는 상대의 의도를 읽는 것"인데, 대회에는 처음 보는 상대가 없습니다.** 같은 봇과 수백 판을 둡니다.

즉 **LLM이 실제로 이득을 주는 곳은 인간 상대**인데, 인간 상대 무대(SCHNAIL)는 규모가 작고 경쟁적 위신이 없습니다. **노력의 보상이 측정되는 곳과 기술이 유효한 곳이 어긋나 있습니다.**

### 4. 그래서 나쁜 아이디어인가 — 아니다. 단, 설계에서 조심할 것

빈 자리가 있는 이유가 "시도해보고 실패해서"가 아니라 **"구조적 인센티브 부재"** 라는 건 좋은 신호입니다. 다만 함정이 있습니다.

#### 4.1 **가장 흔한 실패 모드: 밴딧을 비싸게 재구현하기**

LLM 출력이 `{"build": "4gate"}` 처럼 **미리 정의된 N개 중 하나를 고르는 것**이라면, 당신은 UCB1을 **레이턴시와 비용과 분산을 추가해서** 다시 만든 겁니다. 성능은 거의 확실히 더 나쁩니다.

LLM이 값을 하려면 출력이 **조합적(compositional)** 이어야 합니다:

```
나쁨:  "전략: 4게이트 러시"                    ← 빌드 테이블로 표현 가능 = 밴딧이 더 낫다
좋음:  "3넥 가되 상대 스카우트가 우리 테크를 봤으니
        럴커 2기를 입구에 고정. 앞마당 가스는 뒤로 미룸.
        16분까지 이 자세 유지, 그 전에 뮤탈 보이면 즉시 파기" ← 빌드 테이블로 표현 불가
```

즉 **"FSM에 어떤 파라미터를 어떤 조건부로 주입할 수 있는가"가 액션 문법 설계의 핵심**이고, 이 표현력이 프로젝트의 성패를 가릅니다.

#### 4.2 **평가 설계 — 봇 대 봇으로는 효과가 안 보인다**

3.4의 논리가 그대로 당신에게 적용됩니다. 벤치마크를 이렇게 잡아야 합니다:

- **다전제 적응력**: 같은 상대와 N판 두면서 "같은 방법에 반복해서 지는가" 측정. 기존 봇의 고질병이고 LLM이 직접 겨냥하는 지점.
- **처음 보는 전략에 대한 반응**: 홀드아웃 봇 집합 또는 사람이 직접 변칙 전략 구사.
- **인간 상대(SCHNAIL)**: 규모는 작지만 LLM 우위가 드러나는 유일한 무대.

기존 봇 대상 래더 승률만 보면 **LLM 계층이 아무것도 안 하는 것처럼 보일 것**입니다.

#### 4.3 **BASIL 규칙을 우회하는 합법적 경로: 오프라인 증류**

인터넷 금지 규칙은 **런타임 API 호출**을 막는 것입니다. 우회가 아니라 정당한 설계로 이렇게 할 수 있습니다:

1. 개발 중에는 온라인 LLM 오케스트레이터로 플레이하며 **(상황 → 전략 지시)** 쌍을 대량 수집.
2. 이걸 **결정 테이블 / 소형 모델 / 정책 네트워크로 증류**.
3. 증류 결과물을 **100MB read 디렉터리에 담아 제출.** 런타임 네트워크 호출 0.

이러면 **LLM으로 만든 전략 계층을 규칙 준수 상태로 대회에 출전시킬 수 있습니다.** 이건 실제로 아무도 안 해본 조합이고, "LLM을 봇에 넣는다"보다 논문/프로젝트로서 신규성이 더 큽니다.

#### 4.4 **다만 솔직하게: SC2로 하면 훨씬 쉽다**

순수하게 "오케스트레이터+FSM 구조를 돌려보고 싶다"가 목표라면 SC2가 **압도적으로 합리적**입니다 — PySC2, LLM-PySC2, TextStarCraft2가 다 깔려 있고, 비교할 베이스라인 논문도 있습니다. 브루드워를 고를 이유는 딱 두 가지입니다:

1. **스타1 도메인 지식이 있어서** 액션 문법과 전략 지시를 제대로 설계할 수 있다 (이게 실제로 가장 큰 차별점입니다)
2. **BASIL/SSCAIT라는 객관적 상시 평가 무대**가 있다 (SC2 LLM 에이전트는 대부분 내장 AI 상대 승률만 보고합니다 — 훨씬 약한 평가)

### 5. 요약

| 질문 | 답 |
|---|---|
| FSM + LLM 오케스트레이터 구조가 없나? | **있다.** SwarmBrain이 정확히 그 구조(LLM Overmind + condition-response state machine). LLM-RTS 연구의 표준 설계. |
| 왜 브루드워 대회에는 없나? | **BASIL은 인터넷 접속 금지**, SSCAIT는 32bit Win7 샌드박스, AIIDE는 전체 소스 공개 + 재현성 요구, 대회당 2만 경기 규모. **출전할 무대가 없다.** |
| 대회 밖에서도 왜 없나? | **BW용 언어 래퍼 부재**(SC2는 기성품), **커뮤니티 비중첩**(C++ 취미 ↔ Python 학계), **논문 신규성 소진**, **봇 대 봇에서는 밴딧이 이미 충분**. |
| 좋은 아이디어인가? | **그렇다.** 단 (a) LLM 출력이 조합적이어야 하고, (b) 평가를 다전제 적응력/대인간으로 잡아야 하며, (c) 대회 출전을 원하면 오프라인 증류 경로를 써야 한다. |
