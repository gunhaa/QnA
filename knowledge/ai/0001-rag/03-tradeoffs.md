# RAG 트레이드오프와 선택 기준

## 쉬운 설명

책을 펴 보고 답하게 하면 모르는 것도 답할 수 있지만, 이제 **답의 품질이 "어느 쪽을 펴느냐"에 달린다.** 엉뚱한 쪽을 펴면 똑똑한 학생도 틀린다. 그리고 책을 다 읽히는 대신 몇 쪽만 골라 보여 주기 때문에, 여러 쪽에 흩어진 내용을 종합하는 질문("이 책 전체의 주제는?")에는 약하다. RAG는 **"최신·근거·싼 비용"을 얻고 "검색이라는 새 실패 지점"과 "전체를 보는 눈"을 내준** 선택이다.

## 일반 설명

### 1. 핵심 설계 선택: 얻은 것과 포기한 것

| 설계 선택 | 얻은 것 | 포기한 것 |
|---|---|---|
| 지식을 **모델 밖 색인**에 둔다 | 재학습 없이 문서만 바꿔 갱신, 출처 인용, 권한별 필터 | 검색이 틀리면 답도 틀린다. 실패 지점이 파싱·분할·임베딩·검색·생성으로 늘어난다 |
| 문서를 **조각(chunk)**으로 나눈다 | 프롬프트에 필요한 부분만 넣어 토큰 비용·지연 절감 | 조각 밖의 문맥 손실. 여러 문서를 종합하는 질문에 약하다 |
| **근사** 최근접 이웃(ANN) 검색 | 수백만 벡터에서 수 ms 검색 | 정확 검색 대비 일부 결과 누락(재현율 보통 95~99%를 목표로 조정) |
| 임베딩 **유사도**로 찾는다 | 바꿔 말한 질문도 찾는다 | "비슷한 것"이지 "답이 있는 것"이 아니다. 식별자·숫자에 약하다 → 키워드 검색 병행 |
| 질문마다 검색 후 생성 (2단계) | 지연·비용이 예측 가능 | 한 번 검색으로 안 풀리는 다단계 질문에 약하다 |

수치로 본 검색 품질의 영향 (Anthropic Contextual Retrieval 실험, 상위 20개 조각 기준 검색 실패율):

| 구성 | 실패율 | 기본 대비 |
|---|---|---|
| 기본 임베딩 검색 | 5.7% | — |
| + 조각별 문맥 설명(Contextual Embeddings) | — | −35% |
| + 문맥 BM25 (하이브리드) | 2.9% | −49% |
| + 재순위화 | 1.9% | −67% |

모델을 바꾸지 않고 **검색 구성만으로 실패를 3분의 1로** 줄였다. 품질 개선 여지가 모델보다 검색 쪽에 크다는 뜻이다.

### 2. 대안 비교

| | RAG | 긴 문맥(문서 통째로) | 미세 조정 | GraphRAG | 에이전틱 검색 |
|---|---|---|---|---|---|
| 지식 갱신 | 재색인 (분~시간) | 다음 요청부터 | 재학습 (시간~일) | 그래프 재생성 (비쌈) | 즉시 (색인 없음 또는 기존 색인) |
| 근거 인용 | 쉽다 | 가능 (위치 지정 어려움) | 불가 | 가능 | 쉽다 |
| 질의당 비용 | 낮다 (수천 토큰) | 높다 (전체 토큰, 캐시로 완화) | 낮다 | 전역 질문은 매우 높다 | 높다 (여러 번 호출) |
| 종합 질문 | 약하다 | 강하다 (단, context rot) | 해당 없음 | 강하다 | 중간~강 |
| 규모 | 수백만 문서 | 문맥 창 안 (~수십만~100만 토큰) | 무관 | 중소 규모 | 도구에 달림 |
| 맞는 곳 | 큰·자주 바뀌는 사내 지식, 사실 조회 | 작은 문서 묶음의 분석·요약 | 말투·형식·전문 용어 | 문서 전체의 주제·관계 질문 | 다단계 조사, 코드 탐색 |

수치 예:
- **긴 문맥 vs RAG**: 2026년 비교 실험 하나는 긴 문맥 방식이 정답률은 더 높았지만 질의당 토큰 비용이 RAG의 약 26배였다. 2023년 "Lost in the Middle" 연구는 문맥 가운데 놓인 정보의 활용도가 앞·뒤보다 크게 떨어지는 U자 곡선을 보였고, 문맥이 길수록 품질이 떨어지는 현상(context rot)은 2026년에도 완전히 사라지지 않았다.
- **GraphRAG**: 한 벤치마크에서 전역 검색(global search)은 질문당 프롬프트 토큰이 약 331,000개, 일반 벡터 RAG는 약 900개였다. LazyGraphRAG는 색인 비용을 벡터 RAG 수준(GraphRAG의 0.1%)으로 낮췄다.
- **에이전틱 RAG**: 2026년 비교 연구("Is Agentic RAG worth it?")처럼 개선 폭이 질문 유형에 따라 달라, 비용 대비 효과를 측정하고 도입해야 한다.

### 3. 주요 선택지

#### 3.1 분할 단위 — 문서 구조가 있으면 구조로

| 방식 | 장점 | 단점 | 맞는 문서 |
|---|---|---|---|
| 고정 길이 (500~1,000 토큰, 10~20% 겹침) | 구현이 쉽다, 조각 크기 균일 | 문단·표·조항을 가로지른다 | 구조 없는 긴 글 |
| 구조 기반 (제목 경로·조항·표 행) | 의미 단위 보존, 출처 표시가 정확 | 섹션 길이가 들쭉날쭉 → 너무 긴 섹션은 다시 나눠야 | 규정·위키·매뉴얼 |
| 작은 조각으로 찾고 큰 단위로 넣기 (parent-child) | 검색 정밀도 + 생성 문맥 둘 다 | 저장 구조가 복잡 | 긴 섹션이 많은 문서 |
| 문맥 설명 붙이기 (Contextual Retrieval) | 실패율 −35~49% | 색인 시 조각마다 LLM 호출 비용 | 대명사·생략이 많은 문서 |

#### 3.2 임베딩 모델 — 언어와 반출 제약으로

- **API 모델**(OpenAI, Gemini, Voyage 등): 운영 부담이 없지만 문서가 외부로 나가고, 모델 버전이 바뀌면 전체 재임베딩이 필요하다.
- **자체 호스팅 오픈 모델**(BGE-M3, KURE 등): 데이터가 밖으로 안 나간다. 한국어 벤치마크(KURE 프로젝트, Top-1)에서 KURE-v1이 Recall 0.526으로 `text-embedding-3-large`(0.449)보다 약 8포인트 높았다 → [KURE vs API 모델](../../../inquiry/ai/0044-korean-embedding-kure-vs-api-models.md).
- **차원**: 차원이 클수록 저장·검색 비용이 늘어난다. pgvector `vector` 타입 HNSW는 2,000차원까지라 3,072차원 모델은 `halfvec`이나 차원 축소가 필요하다.
- 여러 밀집 모델을 섞기보다 **밀집 1개 + 키워드 검색**이 효과 대비 단순하다 → [한국어 RAG 임베딩 선택](../../../inquiry/ai/0039-korean-rag-embedding-model-selection-vs-bpe.md#4-여러-가지로-임베딩은-좋지-않은가).

#### 3.3 결과 합치기 — RRF로 시작, 평가 데이터가 생기면 CC 검토

| | RRF | CC (가중 합) |
|---|---|---|
| 입력 | 순위만 | 정규화한 점수 |
| 튜닝 | 거의 없음 (`k = 60`) | 정규화 방식·가중치 `α`를 평가 데이터로 맞춰야 |
| 장점 | 척도가 다른 검색기를 안전하게 합침 | "1등이 압도적"인 신호를 살림 |
| 단점 | 점수 차이 정보를 버림 | 데이터 분포가 바뀌면 다시 맞춰야 |

#### 3.4 재순위화 — 정밀도가 모자랄 때

- 크로스 인코더로 상위 50개를 다시 매기면 실패율이 추가로 줄지만(위 표 2.9% → 1.9%), 후보마다 모델을 돌려 **질의당 수십~수백 ms**가 늘고 GPU나 API 비용이 든다.
- 순서: 평가 세트 → 분할 개선 → 하이브리드 → 재순위화 → 임베딩 모델 교체. 앞 단계가 싸고 효과가 크다.

#### 3.5 저장소 — 이미 PostgreSQL이면 pgvector부터

- **pgvector**: 기존 DB에 확장만 추가, 트랜잭션·조인·권한 필터를 SQL로. 수백만~1천만 벡터까지는 무난하다는 사례가 많다.
- **전용 벡터 DB**(Qdrant, Milvus 등): 수억 벡터, 다중 테넌트, 필터 성능이 중요할 때 → [pgvector vs 전용 Vector DB](../../../inquiry/database/0015-pgvector-vs-dedicated-vector-db.md#4-언제-무엇을-쓰나).

#### 3.6 호출 방식 — 질문 유형으로

- 질문 대부분이 "규정 하나 찾기"면 **2단계 RAG**.
- 잡담과 섞이거나 여러 문서를 오가야 하면 **도구 호출(에이전틱)**. 단, 도구 호출 횟수 상한과 "검색 안 하고 답하기" 방지 지시가 필요하다 → [흔한 함정](./04-pitfalls.md).

#### 3.7 실제 측정 사례 — 공개 데이터셋으로 잰 RAG 백엔드

Markdown 문서(제목 단위 섹션, 한국어)를 색인하는 RAG 백엔드를 직접 만들면서 선택지를 설정으로 바꿔 끼울 수 있게 하고, **공개 한국어 검색 벤치마크(AutoRAG Retrieval)를 Markdown으로 옮긴 평가 세트**(문서 32개·질문 114개, 섹션 단위 MRR@10·Hit@5)로 하나씩 잰 결과다. 규모가 작은 세트라 절댓값보다 선택지 간 차이를 보는 용도다.

| 선택 | 결정 | 근거·대가 |
|---|---|---|
| 분할 단위 | 제목 하나 = 섹션 하나, 1,024토큰을 넘는 섹션만 나눔 (겹침 0) | 512 상한은 실제 PDF 변환본에서 토큰의 24%를 잘랐다. 2048은 검색 성능 근거가 없어 제외. 나눠지는 섹션은 3.1%뿐. 검색은 조각으로, 반환은 섹션 전체로(parent-child), 섹션 점수는 조각 점수의 **최댓값**(합이면 긴 섹션이 유리) |
| 조각 머리말 | 제목 경로를 붙임 | LLM이 쓴 문맥 설명은 색인 비용·비결정성 때문에 보류 |
| 키워드 검색 | 앱에서 형태소 분석(Kiwi) → DB FTS(`simple` 사전, GIN 색인)로 후보 추출 → 앱에서 BM25 점수 | DB 확장 없이 공식 pgvector 이미지 유지. 대신 분석기를 바꾸면 전체 재색인 |
| 임베딩 + 형태소 분석기 교체 | KURE-v3(1024차원) + Kiwi를 **함께** 채택 | 하나씩 바꾸면 각각 +0.025로 유의하지 않았고, 둘을 같이 바꾸자 MRR@10 0.905 → 0.940(+0.035, p 0.045), Hit@5 0.991 → 1.000. 대가: 색인 시간 약 3.2배, JVM 메모리 약 5 GiB, 질의 p50 약 1.8배 |
| 결과 합치기 | CC(점수 정규화 후 벡터 0.3 : BM25 0.7)를 운영 기본값, RRF는 비교 기준선 | 선행 연구에서는 같은 BM25 위 CC가 RRF보다 높았지만(0.733 vs 0.690), 이 세트에서 직접 잰 RRF → CC는 0.911 → 0.905로 **차이 없음**(p 0.713). CC 0.3은 임시 교정값 |
| 재순위화 | 인터페이스만 두고 끔 | 직접 측정은 안 함. 선행 연구에서 개선 폭이 노이즈 범위(+0.024)였고 질의당 약 9초가 늘었다 |

채택 규칙은 "MRR@10이 +0.02 이상 오르고 Hit@5가 떨어지지 않을 때만, 차이가 질문 1~2개 수준이면 더 단순한 쪽"이었다. 같은 장비에서만 비교하고, 평가 때는 HNSW 대신 정확 검색으로 결과를 결정적으로 만들었다. 컴포넌트별 후보·측정값·아직 재지 않은 것은 [실습 문서](./06-labs.md)에 정리했다.

### 4. 쓰지 말아야 할 때

- **문서가 작고 거의 안 바뀐다**: 수십 쪽짜리 매뉴얼이면 문맥에 통째로 넣고 프롬프트 캐시를 쓰는 편이 단순하고 정확하다.
- **답이 계산·집계다**: "지난달 부서별 지출 합계"는 검색이 아니라 SQL·도구 호출(text-to-SQL)로 푼다.
- **모델의 말투·형식을 바꾸고 싶다**: 미세 조정이나 프롬프트 문제다.
- **전체 문서를 종합하는 질문이 대부분이다**: 요약 사전 생성, GraphRAG, 긴 문맥을 검토한다.
- **평가 데이터를 만들 수 없다**: 검색 품질을 측정할 수 없으면 개선도 회귀 감지도 못 한다. 최소 50~100문항부터 만든다 → [RAG 평가 방법](../../../inquiry/ai/0047-rag-evaluation-benchmark-methods-and-tools.md).

### 5. 선택 체크리스트

- [ ] 질문 유형을 분류했나 (사실 조회 / 종합 / 계산 / 잡담)
- [ ] 문서 규모·갱신 빈도에서 긴 문맥보다 RAG가 맞는가
- [ ] 문서 반출이 가능한가 (API 임베딩·LLM 사용 여부)
- [ ] 문서 구조(제목·조항·표)를 분할에 쓸 수 있나
- [ ] 키워드로만 찾히는 것(조항 번호, 코드, 고유명사)이 있나 → 하이브리드
- [ ] 권한별로 보여야 할 문서가 다른가 → 메타데이터 필터 설계
- [ ] 검색 평가 세트(정답 문서·근거 위치 포함)를 만들 수 있나
- [ ] 임베딩 모델 교체 시 전체 재색인 비용을 감당할 수 있나
