# RAG 장애 유형과 대응

## 쉬운 설명

사서 혼자 일하는 게 아니라 **카드 상자, 번역가, 답안 작성자**가 함께 일한다. 카드 상자가 잠기면 책을 못 찾고, 번역가(임베딩 모델)가 바뀌면 옛 카드와 새 질문이 서로 못 알아보고, 답안 작성자(LLM)가 자리를 비우면 답이 안 나온다. 무서운 건 이런 고장의 상당수가 **조용하다**는 점이다. 에러 없이 그럴듯한 답이 계속 나오는데, 점점 덜 맞는다.

## 일반 설명

원인이 대상(검색 색인·임베딩 모델·LLM·저장소)에 있어 **복구·이중화가 필요한** 장애다. 설정·코드를 고쳐 해결하는 문제는 [흔한 함정](./04-pitfalls.md)에 있다. RAG는 구성 요소가 많아 **장애 지점이 여럿**이고, 상당수가 오류 없이 품질만 떨어지는 형태로 나타난다.

### 1. 장애 유형 한눈에 보기

| 장애 유형 | 장애 지점 | 드러나는 방식 | 감지 |
|---|---|---|---|
| 생성 모델 중단·한도 초과 | LLM API | 오류·지연 (시끄럽다) | 오류율, 429·5xx |
| 임베딩 경로 중단 | 임베딩 모델·서버 | 검색 불가 또는 키워드만 | 오류율, 강등 응답 비율 |
| 색인 낡음 (원본과 불일치) | 색인 동기화 | 옛 내용으로 답 (조용하다) | 동기화 지연, 원본·색인 건수 비교 |
| 임베딩 공간 불일치 | 모델 교체·버전 | 검색 품질 급락 (조용하다) | 골든 세트 지표, 평균 유사도 |
| 필터 검색 결과 부족 | ANN 색인 + 필터 | 결과 수 모자람 (조용하다) | 반환 건수 < 요청 k |
| 색인 손상·재구축 중 | 벡터 색인 | 오류 또는 누락 | 색인 검사, 재현율 |
| 지연 폭증·시간 초과 | DB·재순위화·LLM | 시간 초과 | p95·p99 지연 |
| 저장소 장애 | DB 노드 | 전체 검색 불가 | 헬스 체크 |
| 적용 한계 | RAG 방식 자체 | 특정 질문 유형만 틀림 | 질문 유형별 지표 |

### 2. 생성 모델 중단·한도 초과

- **장애 지점**: 외부 LLM API.
- **원인**: 공급자 장애, 요청 한도(429), 모델 폐기(deprecation)·이름 변경(404), 응답 지연.
- **영향**: 검색은 되는데 답이 안 나온다. 도구 호출형 RAG는 한 질문에 LLM을 여러 번 부르므로 한 번만 실패해도 전체가 실패한다.
- **대응**:
  - **모델 폴백 목록**: 1순위 → 2순위 → 경량 모델 순으로, 404·429·5xx에서 다음 모델로 넘긴다.
  - **단계별 시간 제한**: 연결(예: 1초), 호출 1회(예: 20초), 답변 전체 예산(예: 60초)을 따로 두고, 예산을 넘으면 503으로 빨리 실패한다.
  - LLM이 모두 실패하면 검색 결과(조항 제목·원문 링크)만이라도 돌려준다.
  - 모델 폐기 일정을 추적하고, 새 모델로 바꿀 때 골든 세트로 생성 품질을 다시 잰다.

### 3. 임베딩 경로 중단

- **장애 지점**: 임베딩 API 또는 자체 호스팅 임베딩 서버(같은 프로세스 안이면 메모리 부족).
- **원인**: API 장애, GPU·메모리 부족, 모델 파일 손상. 1B급 임베딩 모델을 앱 안에서 돌리면 JVM 메모리가 수 GiB 필요하다.
- **영향**: 질의 임베딩이 안 되면 벡터 검색 전체가 멈춘다. 색인 중이면 새 문서가 반영되지 않는다.
- **대응**:
  - **키워드 검색으로 강등**: 질의 임베딩이 실패하면 BM25·FTS 결과만으로 답하고 응답에 `degraded` 표시를 남긴다. 하이브리드 구성이 장애 대비책도 된다.
  - 색인 트랜잭션은 문서 단위로 묶어, 임베딩이 중간에 실패하면 그 문서 전체를 되돌린다 (반쪽 색인 방지).
  - 자체 호스팅이면 모델 파일을 읽기 전용으로 두고 기동 시 차원 검사를 한다.

### 4. 색인 낡음 — 원본과 색인의 불일치

- **장애 지점**: 원본 저장소 → 색인 동기화 경로.
- **원인**: 동기화 이벤트 유실, 동기화 작업 중단, 삭제·이름 변경 미반영, 쓰기 직후 조회(read-after-write) 경합.
- **영향**: 개정 전 내용이나 **삭제된 문서**를 근거로 답한다. 오류가 없어 사용자가 먼저 알아챈다. 삭제 요청된 개인정보가 계속 검색되면 규정 위반이 된다.
- **대응**:
  - 이벤트만 믿지 말고 **주기적 전수 대조**(예: 1시간마다 + 기동 시)로 빠진 변경을 회수한다.
  - 원본 경로를 문서 식별자로 쓰고 내용 해시가 같으면 건너뛰어, 재동기화를 멱등하게 만든다.
  - 파일 단위로 따로 커밋하고, 일시 오류면 동기화 위치(cursor)를 유지해 다음에 이어서, 내용 오류면 별도 표에 기록해 매번 재시도한다.
  - 지표: 원본 문서 수 vs 색인 문서 수, 마지막 동기화 시각, 동기화 실패 건수.

### 5. 임베딩 공간 불일치

- **장애 지점**: 임베딩 모델·버전.
- **원인**: API 공급자가 같은 이름으로 모델을 바꾸거나, 모델 교체 중 일부만 재임베딩해 **서로 다른 모델의 벡터가 한 색인에 섞인다.** 차원이 같으면 오류 없이 저장·검색된다.
- **영향**: 유사도가 의미를 잃어 검색 품질이 급락한다. 차원이 달라 오류가 나는 경우가 오히려 낫다.
- **대응**:
  - 조각마다 모델 이름·리비전·차원을 저장하고, 질의 시 설정값과 다르면 경고한다. 기동 시 설정 차원과 `vector(N)`이 다르면 **기동을 실패**시킨다.
  - 모델 교체는 **새 색인을 따로 만들어 전체 재임베딩 → 골든 세트로 검증 → 한 번에 전환**(블루·그린)한다. 원본 문서를 보관해야 재임베딩할 수 있다.
  - 리비전을 고정한 자체 호스팅 모델이면 공급자 쪽 변경 위험이 없다.

### 6. 필터 검색 결과 부족

- **장애 지점**: ANN 색인(HNSW) + 메타데이터 필터.
- **원인**: HNSW는 그래프를 따라 가까운 후보를 정해진 수(`ef_search`)만큼 찾은 뒤 필터를 적용한다. 필터가 전체의 일부만 남기면 후보 대부분이 버려진다.
- **영향**: 요청한 20개 중 몇 개만 돌아온다. 한 사례에서는 전체의 10%인 부분 집합을 필터하자 20개 중 평균 3.7개만 채워졌다. 권한·언어별 검색에서 특히 나타난다.
- **대응**:
  - 필터 값 조합별 **부분 색인**(partial HNSW index, 예: 공개 범위 × 언어)을 만들면 20/20이 복구된다.
  - pgvector 0.8.0+ 반복 스캔(`hnsw.iterative_scan`)으로 모자라면 더 찾게 한다(`hnsw.max_scan_tuples` 상한).
  - 테넌트·권한 단위가 크면 파티션이나 별도 테이블로 나눈다.
  - 지표: 반환 건수 < 요청 k 인 비율.

### 7. 색인 손상·재구축

- **장애 지점**: 벡터 색인.
- **원인**: 확장 버그(pgvector 0.8.3은 HNSW vacuum 중 색인 손상 가능성을 고쳤다), 대량 삭제 후 그래프 품질 저하, 재구축 중 잠금.
- **영향**: 검색 오류, 결과 누락, 재구축 동안 쓰기 차단. HNSW는 삭제를 표시만 해 두는 경우가 많아 삭제가 많으면 색인이 부풀고 재현율이 떨어진다.
- **대응**: 확장 버전을 버그 수정판으로 올리고, `REINDEX CONCURRENTLY`로 서비스 중 재구축한다. 정기적으로 정확 검색(색인 없이 전수) 결과와 비교해 재현율을 잰다.

### 8. 지연 폭증·시간 초과

- **장애 지점**: DB 질의, 재순위화 모델, LLM.
- **원인**: 동시 부하, 색인을 못 쓰는 실행 계획(정확 스캔), 재순위화 후보 과다, LLM 응답 지연. 한 법령 RAG 연구에서는 CPU에서 돌린 재순위화 모델이 질의당 약 9초를 더했는데 개선은 노이즈 범위였다.
- **영향**: 사용자 요청 시간 초과, 연결 풀 고갈로 다른 기능까지 영향.
- **대응**: DB 문장 시간 제한(예: 3초), 단계별 시간 예산, 재순위화 후보 수 상한. 평가·일괄 작업은 운영 DB와 분리하거나 한가한 시간에 돌린다.

### 9. 저장소 장애

- **장애 지점**: 벡터·키워드 색인을 담은 DB.
- **영향**: 검색 전체 불가.
- **대응**: 일반 DB 고가용성(복제본, 장애 조치)을 따른다. 벡터 색인은 **원본 문서와 임베딩 모델이 있으면 다시 만들 수 있는 파생 데이터**이므로, 백업보다 "원본 보관 + 재색인 절차·소요 시간 측정"이 핵심이다. 대규모면 재임베딩에 수 시간이 걸리므로 그동안 키워드 검색만으로 운영할지 정해 둔다.

### 10. 적용 한계와 반례

RAG 방식 자체가 맞지 않는 질문 유형이다. 구성 요소가 정상이어도 틀린다.

| 한계 | 반례 | 대응 |
|---|---|---|
| 다단계 추론 | "A 규정의 예외 대상이 B 제도도 쓸 수 있나" — 근거가 두 문서에 흩어짐 | 에이전틱 RAG(재검색), 질의 분해 |
| 전역·종합 질문 | "전체 규정에서 가장 자주 바뀐 영역은?" | 요약 사전 생성, GraphRAG |
| 집계·계산 | "부서별 평균 연차 사용일" | SQL·도구 호출 |
| 문서에 없는 답 | 규정이 정하지 않은 사례 | 거절 응답, 담당자 안내 |
| 문서끼리 모순 | 옛판·새판, 부서별 다른 지침 | 버전·우선순위 메타데이터, 모순 표시 |

Barnett 외(2024)는 실제 시스템 3개에서 실패 지점 7개(내용 누락, 상위 순위에서 놓침, 문맥 통합 한계, 추출 실패, 형식 오류, 구체성 부적절, 불완전한 답)를 정리하고, **RAG는 운영 중에만 검증할 수 있고 견고함은 설계가 아니라 운영으로 쌓인다**고 결론지었다.

### 11. 복구 절차

1. **감지**: 오류율·지연(시끄러운 장애)과 함께, 골든 세트 정기 실행·반환 건수·평균 유사도·동기화 지연(조용한 장애)을 지표로 둔다.
2. **격리**: 어느 단계인지 가른다 — 원본 vs 색인 건수(동기화), 질의 임베딩 성공률(임베딩), 정확 검색 vs 색인 검색 결과(색인), LLM 오류 코드(생성).
3. **조치**: 강등 운영(키워드만, 검색 결과만) → 원인 단계 복구(폴백 모델, 재동기화, 재색인).
4. **정상화 확인**: 골든 세트 지표가 장애 전 수준인지 확인한 뒤 강등을 해제한다.
5. **기록**: 장애 질문을 골든 세트에 추가해 회귀를 막는다.
