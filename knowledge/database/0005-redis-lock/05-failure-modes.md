# Redis 락 장애 유형과 대응

## 쉬운 설명

Redis 락이 제 기능을 못 하는 경우는 크게 둘이다. **게시판(Redis)이 쪽지를 잃어버리거나**(서버가 죽거나 다른 서버로 바뀔 때), **쪽지 주인이 잠깐 멈춘 사이 유효 기간이 끝나는** 경우다. 어느 쪽이든 결과는 같다 — 두 사람이 동시에 자기가 주인이라고 믿는다. 반대로 게시판에 연결이 안 되면 아무도 쪽지를 못 붙여서 일이 멈춘다.

## 일반 설명

> 대상(Redis·락 구조) 쪽 원인으로 락이 제 기능을 못 하는 경우를 다룬다. 사용자가 코드·설정을 고쳐 해결하는 것(TTL 설정, 해제 방식, 축출 정책 등)은 [흔한 함정](./04-pitfalls.md)에 있다. Redis 서버 자체의 장애 조치·영속성은 [Redis 장애 대응과 고가용성](../0002-redis/05-failure-modes.md)에 있다.

### 1. 장애 유형 한눈에 보기

락의 장애는 두 방향으로 나타난다.

| 방향 | 뜻 | 영향 |
|---|---|---|
| **안전성 위반** (동시 보유) | 두 클라이언트가 동시에 락을 가졌다고 믿음 | 중복 실행, 갱신 분실, 이중 처리 |
| **가용성 상실** (획득 불가) | 아무도 락을 잡지 못하거나 오래 기다림 | 작업 정지, 요청 지연·타임아웃 |

| # | 장애 유형 | 장애 지점 | 방향 |
|---|---|---|---|
| 2 | 장애 조치 중 락 유실 | 마스터 → 레플리카 비동기 복제 | 안전성 |
| 3 | 재시작으로 락 소실 | 영속성 없는/지연된 노드 | 안전성 |
| 4 | 보유자 멈춤 중 만료 | 클라이언트 프로세스(GC, VM 정지) | 안전성 |
| 5 | 네트워크 분리 | 클라이언트 ↔ Redis 경로 | 안전성 + 가용성 |
| 6 | 시간 가정 위반 | 시계·지연 (특히 Redlock) | 안전성 |
| 7 | 락 서비스 중단 | Redis 노드·클러스터 | 가용성 |
| 8 | 영구 보유 (고아 락) | 멈춘 보유자 + 자동 연장 | 가용성 |
| 9 | 경합 폭주 | 핫 락 키를 가진 샤드 | 가용성 |

### 2. 장애 조치 중 락 유실

- **장애 지점**: 마스터-레플리카 비동기 복제 (Sentinel, Cluster).
- **원인**: A가 마스터에서 락을 얻은 직후, 복제되기 전에 마스터가 죽는다. 레플리카가 승격되는데 그곳에는 락 키가 없다.
- **영향**: B가 새 마스터에서 같은 락을 얻는다 → A와 B 동시 보유. 장애 조치 순간 보유 중이던 락 여러 개가 한꺼번에 영향받을 수 있다.
- **대응**:
  - 효율용이면 감수한다(장애 조치는 드물고, 결과는 중복 실행 한 번).
  - `WAIT 1 <ms>`로 레플리카 반영을 확인한 뒤 진행하면 확률이 줄어든다. 단, 확인 후에도 승격 대상이 그 레플리카가 아닐 수 있어 **0이 되지는 않는다**.
  - 정확성용이면 fencing token 또는 DB 제약으로 보호 대상에서 막는다 → [개요 §5](./02-overview.md#5-fencing-token).
  - 락 정확성이 가용성보다 중요하면 합의 기반 저장소(etcd, ZooKeeper)로 옮긴다.

### 3. 재시작으로 락 소실

- **장애 지점**: 영속성이 없거나(`appendonly no`) `appendfsync everysec`인 노드의 재시작.
- **원인**: 메모리에만 있던 락 키가 재시작으로 사라진다. `everysec`이면 마지막 1초의 쓰기가 사라질 수 있다.
- **영향**: 재시작 직후 다른 클라이언트가 같은 락을 얻는다. Redlock에서는 한 노드가 락을 잊고 다시 들어오면 **과반이 두 번 성립**할 수 있다.
- **대응**:
  - Redlock은 재시작한 노드를 **최대 TTL 이상 지난 뒤 다시 투입**(지연 재시작)하는 것이 알고리즘의 전제다. 또는 `appendfsync always`(쓰기 성능 비용).
  - 단일 Redis는 재시작 = 모든 락 해제로 보고, 정확성은 보호 대상에서 지킨다.

### 4. 보유자 멈춤 중 만료

- **장애 지점**: 락을 가진 클라이언트 프로세스.
- **원인**: Stop-the-world GC, 컨테이너 CPU 쓰로틀링, VM 일시 정지·라이브 마이그레이션, 스왑으로 프로세스가 TTL보다 오래 멈춘다. 프로세스는 이 사실을 모른다.
- **영향**: 깨어난 A는 "아직 내 락"이라 믿고 쓰기를 계속한다. 그 사이 B가 락을 얻어 같은 자원을 쓰고 있다. **자동 연장(watchdog)도 막지 못한다** — 연장하는 스레드도 같이 멈추기 때문이다.
- **대응**:
  - 이 장애 유형은 **어떤 lease 기반 락에서도** 생긴다(Redis에만 해당하지 않음). 락 쪽에서 막을 수 없고, 보호 대상이 fencing token으로 오래된 쓰기를 거부해야 한다.
  - 완화: 중요한 쓰기 직전에 남은 TTL을 확인(`PTTL`), GC 튜닝(ZGC 등 짧은 정지), 컨테이너 CPU limit 여유. 확인과 쓰기 사이에도 멈출 수 있으므로 **완화일 뿐**이다.

### 5. 네트워크 분리

- **장애 지점**: 클라이언트와 Redis 사이 네트워크.
- **원인과 영향**:

| 상황 | 영향 |
|---|---|
| 보유 중 A가 Redis와 끊김 | A는 연장도 해제도 못 함 → TTL 뒤 만료 → B 획득. A가 끊긴 줄 모르고 작업을 계속하면 **동시 실행** |
| 해제 명령이 전달 안 됨 | 락이 TTL까지 남음 → 다른 클라이언트 대기 |
| 획득 응답이 유실됨 (Redis는 성공 처리) | 클라이언트는 실패로 알고 재시도 → 자기 락에 막혀 TTL까지 대기 |
| 클라이언트 다수가 끊김 | 락 획득 실패율 급증 → 작업 정지 |

- **대응**:
  - 연장 실패를 **작업 중단 신호**로 쓴다. Redisson은 watchdog 연장 실패를 로그로만 남기므로, 긴 작업은 단계마다 `isHeldByCurrentThread()`·`remainTimeToLive()`를 확인한다.
  - 획득 재시도 시 **같은 토큰**을 쓰면 "응답 유실" 경우에 자기 락을 다시 인정할 수 있다.
  - 정확성은 fencing으로.

### 6. 시간 가정 위반

- **장애 지점**: 시계와 지연에 대한 가정. 주로 Redlock.
- **원인**: Redlock은 "획득에 걸린 시간 < TTL"과 "노드들의 시간이 비슷한 속도로 흐른다"를 가정한다. NTP가 시계를 크게 보정하거나, 패킷이 TTL만큼 지연되면 가정이 무너진다.
- **영향**: 한 노드에서 키가 예상보다 일찍 만료 → 과반이 다른 클라이언트에게 넘어감 → 동시 보유.
- **대응**: 시계를 점진 보정(slew)하게 설정하고 큰 점프를 막는다. TTL을 네트워크 지연·시계 오차보다 충분히 길게 둔다. 근본적으로는 [Redlock 논쟁](./01-history.md#3-redlock-논쟁의-요지)의 결론대로 fencing이 필요하다.

### 7. 락 서비스 중단

- **장애 지점**: 락용 Redis(단일 인스턴스) 또는 클러스터에서 해당 슬롯을 가진 샤드.
- **원인**: 프로세스 종료, 메모리 부족(OOM), 장애 조치 진행 중(수 초~수십 초), 긴 블로킹 명령.
- **영향**: 모든 락 획득이 실패하거나 타임아웃. 락 뒤의 작업 전체가 멈춘다. 락 획득을 동기 요청 경로에 둔 API는 **응답 지연·오류로 번진다**.
- **대응**:

| 단계 | 조치 |
|---|---|
| 설계 | 락 실패 시 동작을 미리 정한다: **닫힘(fail-closed)** — 작업하지 않음(정확성 우선), **열림(fail-open)** — 락 없이 진행(효율용만) |
| 설계 | 획득에 짧은 타임아웃(수백 ms)과 서킷 브레이커 |
| 운영 | Sentinel/Cluster로 자동 장애 조치. 장애 조치 중에는 §2의 유실을 감수 |
| 복구 | 복구 후 락이 비어 있으므로 진행 중이던 작업이 중복 실행될 수 있다 → 작업은 멱등하게 |

### 8. 영구 보유 (고아 락)

- **장애 지점**: 멈췄지만 죽지 않은 보유자 + 자동 연장.
- **원인**: 보유 스레드가 데드락·무한 대기에 빠졌는데, watchdog은 별도 스레드라 **프로세스가 살아 있는 한 계속 연장**한다.
- **영향**: 해당 락을 기다리는 모든 작업이 무기한 정지. TTL이 있는데도 풀리지 않아 원인 파악이 늦다.
- **대응**:
  - **감지**: 락 보유 시간 메트릭(획득~해제), 같은 락 키가 일정 시간 이상 존재하면 경보. 값(Redisson은 `UUID:threadId`)으로 보유 인스턴스·스레드를 찾는다.
  - **조치**: 보유 인스턴스의 스레드 덤프로 멈춘 원인 확인 → 인스턴스 재시작(연장이 멈춰 TTL 뒤 해제). 수동 `DEL`은 보유자가 아직 쓰고 있을 수 있으므로 **보유 프로세스를 먼저 멈춘 뒤에** 한다.
  - **예방**: 작업 자체의 타임아웃 → [흔한 함정 §5](./04-pitfalls.md#5-redisson-leasetime을-주면-watchdog이-꺼진다-오해).

### 9. 경합 폭주

- **장애 지점**: 인기 락 키(핫 키)를 가진 Redis 샤드.
- **원인**: 많은 클라이언트가 한 락을 동시에 노린다. 해제 순간 대기자 전체가 재시도(thundering herd)하고, Pub/Sub 방식이면 해제마다 대기자 전원에게 메시지가 간다.
- **영향**: 해당 샤드 CPU 포화 → 같은 샤드의 다른 키(캐시 등)까지 느려짐 → 락 획득 타임아웃 → 재시도가 더 몰리는 악순환.
- **대응**: 감지는 `INFO commandstats`의 `set`·`evalsha` 호출 급증, Redis 8.6+의 `HOTKEYS`. 조치는 획득 재시도에 백오프·지터·상한, 대기 대신 즉시 포기로 전환. 근본적으로는 락 단위를 쪼개거나(파티셔닝) 락 대신 원자 명령·큐로 바꾼다.

### 10. 배포 형태별 고가용성 동작

| 배포 | 노드 1대 장애 | 장애 조치 중 | 보유자 멈춤 |
|---|---|---|---|
| 단일 인스턴스 | 락 서비스 중단, 재시작 시 모든 락 소실 | — | 동시 보유 가능 |
| Replica + Sentinel | 수 초~수십 초 중단 후 복구 | 복제 안 된 락 유실 | 동시 보유 가능 |
| Cluster | 해당 샤드의 락만 영향 | 해당 샤드 락 유실 가능 | 동시 보유 가능 |
| Redlock 5대 | 영향 없음(과반 유지) | 해당 없음(복제 없음) | 동시 보유 가능 |
| etcd / ZooKeeper (비교) | 과반 유지 시 영향 없음 | 합의로 유실 없음 | **동시 보유 가능** — 그래도 fencing 필요 |

마지막 열이 핵심이다. **보유자 멈춤은 어떤 락 저장소도 막지 못한다.** 저장소의 선택은 "Redis 쪽 장애로 락이 사라지는 경우"를 줄일 뿐이고, 정확성은 보호 대상의 fencing·제약이 지킨다.

### 11. 복구 절차

| 단계 | 조치 |
|---|---|
| 1. 감지 | 해제 실패("내 락 아님") 급증, 같은 작업 중복 실행 로그, 락 대기 시간 p99 급증, 락 키 장기 존재 경보, Redis 장애 조치 이벤트 |
| 2. 범위 확인 | 장애 시간대에 락으로 보호된 작업 목록. 장애 조치 시각과 대조해 동시 실행 가능 구간을 특정 |
| 3. 조치 | 고아 락: 보유 프로세스 정지 → 키 삭제. 서비스 중단: fail-closed/open 정책대로, 재시도 폭주 차단 |
| 4. 정상화 | 동시 실행 구간의 데이터 정합성 검사(중복 처리·음수 재고 등) 후 보정. 작업이 멱등하면 재실행 |
| 5. 재발 방지 | 정확성용 락에 fencing·DB 제약 추가, 작업 타임아웃 < TTL, 락용 Redis 분리 |
