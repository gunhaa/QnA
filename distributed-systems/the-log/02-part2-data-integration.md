### 1. "데이터 욕구 5단계설" — 왜 대부분의 회사가 순서를 거꾸로 하는가

저자는 Maslow의 욕구 위계를 데이터에 빗댑니다.

```
                    ▲ 상위
            ┌───────────────────┐
            │  예측 / 최적화 /    │  ← 모두가 하고 싶어하는 것
            │  실험 / ML         │
            ├───────────────────┤
            │  집계 / 분석 /      │
            │  시각화            │
            ├───────────────────┤
            │  정제 / 변환 /      │
            │  스키마 부여        │
            ├───────────────────┤
            │  신뢰할 수 있고     │  ← 실제로 먼저 해결해야 하는 것
            │  완전한 데이터 흐름  │
            ├───────────────────┤
            │  데이터 수집        │
            └───────────────────┘
                    ▼ 기반
```

저자의 지적:

> 대부분의 조직은 이 기반을 건너뛰고 상위의 정교한 처리부터 쫓아간다 — **"completely backwards."**

이 진단의 힘은 지금도 유효합니다. 2026년 현재로 번역하면: **"LLM/RAG 파이프라인을 붙이기 전에, 사내 데이터가 애초에 한 곳에서 신뢰성 있게 흐르고 있는지부터 보라"** 는 말과 같습니다. 데이터 기반이 없는 상태에서 상위 기능을 만들면, 기능 자체보다 데이터를 끌어오는 배관에 인력의 대부분이 소모됩니다 — 저자 본인이 2008년에 겪은 일이 정확히 그것입니다(아래 4절).

> **관련:** 이 저장소의 [`ai-llm-basics/`](../../ai-llm-basics/) 문서들에서 다루는 RAG·벡터 임베딩도 결국 "원본 데이터를 임베딩 인덱스라는 또 하나의 projection으로 만드는 일"입니다. Part 1의 관점에서 보면 벡터 DB는 로그의 새로운 투영 대상 중 하나일 뿐입니다.

### 2. 두 가지 복잡화 요인 (Two complications)

저자는 데이터 통합이 **최근 들어 훨씬 어려워진** 이유를 두 가지 동시 발생 트렌드로 설명합니다.

#### (1) 이벤트 데이터의 폭발

전통적으로 DB에 저장되던 것은 "비즈니스 엔티티의 현재 상태"(사용자, 주문, 상품)였습니다. 이제는 그것에 더해 **"일어난 일" 자체**가 데이터가 됩니다:

- 사용자 활동 로그(클릭, 노출, 스크롤, 검색)
- 기계 메트릭(CPU, 지연시간, 에러율)
- 금융 거래 이벤트
- RFID/IoT 센서 추적

핵심은 **양의 차이가 질의 차이를 만든다**는 점입니다. 이벤트 데이터는 전통적 DB 데이터보다 **몇 자릿수(orders of magnitude) 많습니다.** 사용자 1명 레코드에 대해 그 사용자가 만드는 클릭 이벤트는 수만 건입니다. 이 볼륨에서는 "일단 RDB에 넣고 나중에 생각하자"가 성립하지 않습니다.

> **용어:** 이 구분은 오늘날 **fact vs. dimension**, 또는 **event stream vs. entity state**, Kafka Streams의 **KStream vs. KTable** 구분으로 이어집니다. Part 1의 로그/테이블 이중성이 데이터 종류의 분류로 확장된 것입니다.

#### (2) 특화된 데이터 시스템의 폭발

원문 시점(2013) 기준 "지난 5년간" 등장한 시스템들:

| 용도 | 당시 대표 시스템 | 2026년 대표 |
|---|---|---|
| OLAP / 분석 | Vertica, Greenplum | ClickHouse, Druid, Pinot, Snowflake, BigQuery |
| 검색 | Lucene, SOLR, Elasticsearch | Elasticsearch/OpenSearch, Vespa |
| 배치 처리 | Hadoop MapReduce | Spark, Trino |
| 그래프 | Neo4j, 자체 그래프 서비스 | Neo4j, TigerGraph |
| KV / 캐시 | Voldemort, Redis, Memcached | Redis, DynamoDB, ScyllaDB |
| 문서/온라인 | Espresso, MongoDB | MongoDB, DynamoDB |
| 벡터 | (없음) | pgvector, Milvus, Qdrant, Pinecone |

> **관련 문서:** 이 저장소의 [`database/clickhouse/`](../../database/clickhouse/) 문서들이 다루는 ClickHouse가 바로 "OLAP 전용 특화 시스템"의 2026년 대표 주자이고, 그 append-only·컬럼 지향 설계는 이 글의 로그 철학과 직접 맞닿아 있습니다.

#### (3) 두 트렌드의 곱 = 조합 폭발

이 둘이 겹치면 문제가 곱셈으로 커집니다.

```
        [Oracle]  [User DB]  [활동 로그]  [메트릭]        ← N개 소스
            │  ╲    │   ╲     │    ╲       │
            │   ╲   │    ╲    │     ╲      │              각 쌍마다
            ▼    ╲  ▼     ╲   ▼      ╲     ▼              전용 파이프라인
        [Hadoop] [검색] [모니터링] [추천] [DW] [캐시]      ← M개 목적지

        필요한 파이프라인 수 = N × M  (최악의 경우 O(N²))
```

원문의 표현:

> "Connecting all of these would have lead to building custom piping between each pair of systems something like this... This clearly would take an army of people to build and would never be operable."

**O(N²) 문제**의 실질적 고통은 파이프라인 개수 자체보다 다음에 있습니다:

- 각 파이프라인이 자체 스키마 가정, 자체 재시도 로직, 자체 장애 모드를 가짐
- 새 시스템 하나 추가 = 기존 N개 전부와의 연결 작업
- 한 소스의 스키마 변경 = 그에 연결된 모든 파이프라인 동시 수정
- **소유권 불분명** — 파이프라인은 양쪽 팀 중 누구의 것도 아님 → 고아 코드가 됨

마지막 항목이 기술 문제가 아니라 **조직 문제**라는 점이 중요합니다. 이 글의 해법도 결국 조직적 해법입니다(아래 5절).

### 3. Log-structured data flow — 해법

> The solution involves **"a central log for real-time subscription."** Each data source becomes its own log; subscribing systems read, apply changes to their stores, and advance their position.

```
   [Oracle]   [User DB]  [활동 이벤트]  [메트릭]
      │           │           │            │
      └───────────┴─────┬─────┴────────────┘
                        ▼  publish
        ╔═══════════════════════════════════╗
        ║   중앙 로그 (Kafka)                 ║
        ║   토픽별 append-only, 오프셋 부여    ║
        ╚═══════════════════════════════════╝
                        │  subscribe (각자 자기 오프셋 보유)
      ┌──────┬──────────┼──────────┬────────┐
      ▼      ▼          ▼          ▼        ▼
  [Hadoop] [검색]   [모니터링]   [추천]    [DW]

        필요한 연결 수 = N + M
```

원문이 정리한 이 구조의 이점 네 가지:

| 이점 | 설명 | Part 1과의 연결 |
|---|---|---|
| **논리적 타임스탬프 제공** | 모든 소비자가 "어디까지 봤는지"를 오프셋 정수 하나로 표현 | Part 1의 "복제본 = 정수 하나" |
| **생산자/소비자 간 비동기 버퍼** | 느린 소비자가 빠른 생산자를 막지 않음. 소비자 장애가 생산자에 전파되지 않음 | 로그의 내구성 |
| **소스 시스템 종류로부터의 독립** | 소비자는 원본이 Oracle인지 이벤트인지 알 필요 없음 | 로그가 공통 인터페이스 |
| **파이프라인 수정 없이 소비자 추가** | 새 시스템은 기존 로그를 처음부터 읽으면 됨 | 로그 ⊃ 테이블 (과거 재생 가능) |

**"비동기 버퍼"** 항목이 특히 실무적으로 중요합니다. 점대점 파이프라인에서는 다운스트림 장애가 업스트림으로 역전파(backpressure → 장애 전파)됩니다. 중앙 로그는 그 사이에 **내구성 있는 버퍼**를 끼워 넣어 **장애 격리(failure isolation)** 를 만듭니다. Kafka가 단순 메시지 큐와 결정적으로 다른 지점이 여기입니다 — 메시지를 소비 후 삭제하지 않고 보존 기간 동안 유지하므로, 소비자가 몇 시간 죽어 있어도 데이터가 사라지지 않고 복구 후 따라잡을 수 있습니다.

> **관련 문서:** 이 저장소의 [`kafka/kafka-vs-rabbitmq.md`](../../kafka/kafka-vs-rabbitmq.md)가 다루는 "큐 vs 로그" 차이의 사상적 근거가 정확히 이 절입니다. RabbitMQ는 전달 후 삭제하는 브로커이고, Kafka는 **보존되는 로그**입니다.

### 4. At LinkedIn — 실화

이 글의 설득력 대부분이 이 절에서 나옵니다. 추상적 주장이 아니라 실제 실패담이기 때문입니다.

#### LinkedIn의 시스템 진화

중앙집중 Oracle DB 하나로 시작 → 확장 압력에 따라 특화 시스템으로 분화:

- **Search** — 검색 인덱스
- **Social Graph** — 인맥 그래프 서비스
- **Voldemort** — 분산 KV 스토어 (Dynamo 계열)
- **Espresso** — 분산 문서 스토어
- **Hadoop** — 배치 분석
- **Databus** — **"providing a log caching abstraction on top of Oracle tables"** (Oracle 테이블 위의 로그 캐싱 추상화)

**Databus가 중요합니다.** LinkedIn은 이미 "DB 변경을 로그로 뽑아 배포한다"는 아이디어(=CDC)를 갖고 있었습니다. 즉 Kafka는 무에서 나온 게 아니라, Databus의 아이디어를 **DB에 종속되지 않는 범용 시스템으로 일반화**한 결과입니다.

#### 2008년 Hadoop 프로젝트 — 결정적 경험

저자의 회고(요지):

> 계획: **"데이터 옮기는 데 몇 주, 나머지 시간은 알고리즘에."**
> 현실: **데이터 파이프라인 작업이 프로젝트 전체를 잡아먹었다.**

소스마다 커스텀 설정을 만들었고, 그 결과:

- 취약함(fragile) — 업스트림 변경 하나에 깨짐
- 커버리지 제한 — 결국 일부 데이터만 Hadoop에 들어옴
- 유지보수 지옥 — 소스가 늘 때마다 선형 이상으로 비용 증가

여기서 나온 통찰: **커스텀 파이프라인 N²개를 만들지 말고, 범용 파이프라인 하나를 만들자.**

#### Kafka의 탄생

원문의 요약: Kafka는 **메시징 시스템의 개념 + 데이터베이스 로그의 원리**를 결합한 것입니다.

```
        메시징 시스템에서 가져온 것          DB 로그에서 가져온 것
        ─────────────────────────         ──────────────────────
        · 발행/구독 모델                    · append-only 구조
        · 다중 구독자                       · 순서 보장
        · 토픽/파티션 개념                   · 디스크 영속성
        · 클라이언트 API                     · 오프셋 기반 위치 추적
                          ╲             ╱
                           ▼           ▼
                        ┌─────────────────┐
                        │      Kafka      │
                        └─────────────────┘
```

이 조합이 왜 새로웠는가: 당시 메시징 시스템(JMS, AMQP 계열)은 **메시지를 소비 후 삭제**했고, 브로커가 소비자별 전달 상태를 관리했습니다. Kafka는 이를 뒤집어 **브로커는 로그만 유지하고, "어디까지 읽었는지"는 소비자가 관리**하게 했습니다. 이 한 가지 결정에서 다음이 전부 따라 나옵니다:

- 브로커가 소비자 상태를 관리하지 않으므로 소비자 수에 대한 확장성이 O(1)
- 같은 데이터를 여러 소비자가 서로 다른 속도로 읽을 수 있음
- **재생(replay)** 이 가능 — 오프셋을 되감으면 과거를 다시 읽음 (Part 3의 재처리 논증의 기반)
- 브로커 로직이 극단적으로 단순 → 성능 최적화 여지가 큼 (아래 7절)

#### 당시 규모

> LinkedIn: **"over 60 billion unique message writes through Kafka per day"** (하루 600억 건 이상의 고유 메시지 쓰기)

### 5. ETL과 데이터 웨어하우스와의 관계 — 조직 설계 논증

이 절은 기술 논증처럼 보이지만 실제로는 **조직 설계 논증**입니다. 이 글에서 가장 통찰적인 부분 중 하나입니다.

#### 전통적 ETL의 구조적 문제

전통적 ETL은 두 가지 서로 다른 일을 하나로 묶습니다:

1. **데이터 정제(cleanup)** — 원본 시스템의 지저분한 데이터를 의미 있게 만드는 일
2. **웨어하우스 적재 준비** — 특정 DW의 스키마·포맷에 맞추는 일

그리고 이 두 가지를 모두 **중앙 DW 팀**이 수행합니다. 여기서 문제가 발생합니다:

| 문제 | 설명 |
|---|---|
| **조직적 병목** | DW 팀 한 팀이 회사의 모든 팀에서 오는 모든 데이터를 처리 → 팀 수에 비례해 부하 증가, 인원은 그만큼 못 늘어남 |
| **지식 비대칭** | 데이터의 의미를 가장 잘 아는 건 **생산 팀**인데, 정제는 **DW 팀**이 함 → 오해와 왕복 소통 |
| **인센티브 어긋남** | 생산 팀은 더러운 데이터를 내보내도 비용을 치르지 않음 → 품질 개선 동기 없음 |
| **배치 전용** | ETL이 야간 배치 전제 → 실시간 소비자는 아예 서비스 대상 밖 |

#### 저자의 분해안

```
  [생산 팀]                 [중앙 로그]              [소비 시스템]
      │                         │                        │
  ① 정제(cleanup)          ② 실시간 변환             ③ 목적지별 집계
  무손실·가역적 형태로       로그 → 파생 로그            적재 시 변환
  발행                     (join, filter, enrich)     (DW 스키마 맞추기)
```

| 단계 | 담당 | 원칙 |
|---|---|---|
| **① 정제** | **데이터 생산자** | 발행 **전에** 정제. **lossless, reversible**(무손실·가역적) 형태로 — 즉 정보를 버리지 않음 |
| **② 실시간 변환** | 스트림 처리 잡 | 로그를 읽어 파생 로그를 생산. 조인/필터/보강 |
| **③ 목적지별 집계** | 적재 시점 | DW든 검색 인덱스든 각 시스템에 맞는 최종 변환 |

**핵심 전환: 정제 책임이 생산자에게 간다.**

> This shifts responsibility to data producers, making the system **organizationally scalable.**

이제 DW 팀은 "구조화된 피드를 적재하고 시스템 특화 변환을 하는 일"만 합니다. 각 생산 팀이 자기 데이터의 품질을 책임지므로, 팀이 늘어도 중앙 병목이 생기지 않습니다.

> **"lossless, reversible"이 핵심 제약:** 생산자가 정제하되 **정보를 버려서는 안 됩니다.** 예를 들어 "결제 금액을 반올림해서 발행"하면 되돌릴 수 없습니다. Part 1의 "로그 ⊃ 테이블" 원칙이 여기 정책으로 구현된 것입니다 — 로그는 모든 하위 시스템의 원본이므로, 로그 단계에서 버린 정보는 영원히 잃습니다.

#### 스키마의 역할 — 조직 계약으로서의 Avro

이 분해가 작동하려면 생산자와 소비자 사이에 **강제되는 계약**이 있어야 합니다. LinkedIn의 답은 **모든 Kafka 데이터에 Avro 스키마를 등록하도록 강제**하는 것이었습니다.

스키마가 하는 일:

- **호환성 검사** — 스키마 변경 시 기존 소비자를 깨는지 자동 검증(backward/forward compatibility)
- **문서화** — 필드 의미가 코드가 아닌 스키마에 기록됨
- **사회적 프로세스 강제** — 스키마 리뷰가 생산자·소비자가 만나는 지점이 됨

> 이것이 오늘날 **Schema Registry**(Confluent Schema Registry, AWS Glue Schema Registry, Apicurio)의 기원입니다. 2026년 기준으로도 이벤트 기반 아키텍처의 실패 원인 1위가 스키마 거버넌스 부재라는 점에서, 이 글이 2013년에 이걸 짚은 건 선견지명입니다.

#### "Where should we do this processing?"

저자의 답은 교조적이지 않습니다: **조직에 맞는 곳에서 하라.** 정제를 업스트림에서 해도 되고, 로그 위 실시간 변환으로 해도 되고, 목적지 시스템 적재 시 집계로 해도 됩니다. 중요한 건 **위치의 선택지가 존재한다**는 것 — 중앙 로그가 있어야 이 선택지가 생깁니다.

### 6. Log Files and Events — 이벤트 발행의 실제

원문의 예시: **채용 공고가 화면에 표시되었다**는 사건.

**나쁜 구조 (점대점 결합):**

```java
// 공고를 보여주는 코드가 관심 있는 모든 시스템을 알아야 함
renderJob(job);
recommendationService.recordImpression(user, job);   // 추천
securityService.checkScraping(user, job);            // 어뷰징 탐지
analyticsService.trackView(user, job);               // 분석
billingService.countImpression(job);                 // 과금
// ... 새 시스템이 생길 때마다 이 코드를 수정해야 함
```

**로그 기반 구조:**

```java
// 표시 코드는 "일어난 일"만 기록하고 끝
renderJob(job);
eventLog.publish(new JobImpression(user, job, timestamp, context));
```

이후 추천·보안·분석·과금 시스템이 **각자** 그 토픽을 구독합니다. 표시 로직은 누가 듣는지 전혀 모릅니다.

이 구조의 장점:

| 측면 | 효과 |
|---|---|
| **결합도** | 생산자가 소비자를 모름 → 새 소비자 추가 시 생산자 코드 변경 0 |
| **장애 격리** | 추천 시스템이 죽어도 공고 페이지는 정상 동작 |
| **지연시간** | 요청 경로에서 5개의 동기 호출이 사라짐 |
| **재처리** | 새 추천 모델이 지난 30일 노출 데이터를 처음부터 다시 학습 가능 |
| **일관성** | 모든 소비자가 **동일한 이벤트 정의**를 봄 → "노출 수"가 팀마다 다르게 계산되는 문제 소멸 |

마지막 항목이 실무에서 가장 값집니다. 점대점 구조에서는 각 팀이 자기만의 집계 로직을 갖게 되어 "우리 대시보드는 100만인데 저쪽은 87만"이라는 분쟁이 필연적으로 발생합니다. 중앙 로그는 **단일 사실 원천(single source of truth)** 을 강제합니다.

LinkedIn은 이 방식으로 Kafka를 **"the central, multi-subscriber event log"** 로 쓰며 수백 종류의 이벤트 타입을 운영했습니다.

### 7. Building a Scalable Log — 왜 이게 실제로 빠른가

"중앙 로그 하나에 회사의 모든 데이터를 넣는다"는 발상에 대한 즉각적 반론은 **"그게 병목이 되지 않느냐"** 입니다. 이 절이 그 반론에 대한 답입니다. 네 가지 최적화가 있습니다.

#### (1) 파티셔닝 — 전순서의 전략적 포기

> **"Each partition is a totally ordered log, but there is no global ordering between partitions."**

```
Topic: user-clicks
┌─ Partition 0 ─────────────────────┐   각 파티션은 독립된 로그
│ 0 │ 1 │ 2 │ 3 │ 4 │               │   → 독립된 서버에 배치 가능
├─ Partition 1 ─────────────────────┤   → 독립적으로 append 가능
│ 0 │ 1 │ 2 │                       │   → 조정(coordination) 불필요
├─ Partition 2 ─────────────────────┤
│ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │       │   파티션 간 순서는 정의되지 않음
└───────────────────────────────────┘
```

이것이 Part 1에서 예고한 **이론적 순수성의 대가**입니다. 전역 전순서를 포기하는 대신 수평 확장을 얻습니다.

실무적 귀결 — **파티션 키 설계가 순서 보장 범위를 결정합니다:**

- `user_id`로 파티셔닝 → 같은 사용자의 이벤트는 순서 보장, 사용자 간에는 보장 없음
- `order_id`로 파티셔닝 → 주문 단위 순서 보장
- 키 없이 라운드로빈 → 순서 보장 없음, 최대 처리량

> **함정:** "사용자 테이블과 주문 테이블의 변경을 서로 다른 토픽으로 흘리면 두 토픽 간 순서 보장이 없다" — 이 때문에 CDC로 여러 테이블을 복제할 때 외래 키 제약 순서가 깨질 수 있습니다. Debezium 사용 시 흔히 부딪히는 문제이며, 해법은 (a) 관련 테이블을 같은 키로 같은 토픽에 넣거나 (b) 소비 측에서 최종 일관성을 허용하는 것입니다. 이 글은 이 문제를 다루지 않습니다.

#### (2) 배칭 — 작은 연산을 큰 연산으로

> "group small reads and writes together into larger, high-throughput operations"

배칭이 적용되는 지점이 **네 군데 전부**라는 점이 중요합니다:

```
[클라이언트] ──①배치 전송──▶ [브로커] ──②배치 디스크 쓰기──▶ [페이지 캐시/디스크]
                                 │
                                 ├──③배치 복제──▶ [팔로워 브로커]
                                 │
                                 └──④배치 전송──▶ [컨슈머]
```

배칭이 효과적인 이유: 메시지 하나당 고정 비용(시스템 콜, 네트워크 왕복, 디스크 seek, 프로토콜 헤더)이 페이로드 크기와 무관하게 발생하기 때문입니다. 1KB 메시지 1000개를 개별 전송하면 고정 비용 1000회, 1MB로 묶으면 1회입니다.

> **트레이드오프:** 배칭은 **처리량을 지연시간과 맞바꿉니다.** Kafka의 `linger.ms`가 이 손잡이입니다 — 0이면 최저 지연·최저 처리량, 크게 잡으면 그 반대. 이 글은 처리량 쪽을 강하게 밀지만, 2026년의 많은 실시간 유스케이스(결제 승인, 실시간 입찰)에서는 반대 선택이 맞습니다.

#### (3) 순차 I/O — 로그 구조의 본질적 이점

> "A log, like a filesystem, is easy to optimize for linear read and write patterns."

이것이 로그 추상화의 **성능적 정당화**입니다. append-only라는 제약이 곧 순차 접근을 보장하기 때문입니다.

| 접근 패턴 | HDD (2013 기준) | NVMe SSD (2026 기준) |
|---|---|---|
| 랜덤 I/O | ~100 IOPS, 실질 수 MB/s | ~1M IOPS, 수 GB/s |
| 순차 I/O | 100~200 MB/s | 3~14 GB/s |
| 격차 | **수백~수천 배** | **수 배** (여전히 유의미) |

여기서 나오는 유명한 결과: **"디스크가 느리다"는 통념은 랜덤 접근에만 참이다.** 순차 접근 시 디스크는 네트워크보다 빠를 수 있습니다.

더 중요한 건 **OS 페이지 캐시의 활용**입니다. Kafka는 자체 캐시를 두지 않고 OS 페이지 캐시에 의존합니다:

- JVM 힙에 데이터를 들고 있지 않음 → GC 압력 없음
- 브로커 프로세스 재시작 시에도 캐시가 유지됨
- 최신 데이터를 읽는 소비자(대부분의 경우)는 **디스크를 전혀 건드리지 않음** — 페이지 캐시에서 바로 나감

#### (4) 제로 카피 — 포맷 통일의 배당금

> Kafka maintains "a simple binary format...between in-memory log, on-disk log, and in network data transfers"

**같은 바이트 포맷**을 메모리·디스크·네트워크에서 그대로 쓰기 때문에, 변환 없이 `sendfile(2)` 시스템 콜로 커널 공간에서 직접 전송할 수 있습니다.

```
일반적인 경로 (4회 복사 + 4회 컨텍스트 스위치):
  디스크 → 커널 페이지 캐시 → 앱 버퍼 → 커널 소켓 버퍼 → NIC

sendfile 경로 (0~1회 복사 + 2회 컨텍스트 스위치):
  디스크 → 커널 페이지 캐시 ─────────────────────────→ NIC
```

> **2026년 주의:** 제로 카피는 **TLS 암호화를 켜면 상당 부분 무효화**됩니다. 암호화하려면 데이터를 유저 공간(또는 커널 TLS)으로 가져와야 하기 때문입니다. 압축 역시 브로커가 재압축해야 하는 경우 깨집니다. 사내망 평문 통신을 전제했던 2013년과 달리, 전송 구간 암호화가 기본인 현재는 이 최적화의 실질 이득이 줄었습니다. (그래서 `ssl` 활성화 시 Kafka 처리량이 눈에 띄게 떨어지는 현상이 나타납니다.)

#### 네 최적화의 종합

이 네 가지가 합쳐져 나오는 결론은 **"중앙 로그는 병목이 아니라 오히려 가장 싼 경로"** 라는 것입니다. 각 시스템이 개별적으로 소스 DB에 쿼리를 날리는 것보다, 로그에서 순차로 긁어가는 게 압도적으로 저렴합니다. 이것이 "모든 걸 중앙 로그에 넣자"는 급진적 제안이 실제로 성립했던 이유입니다.

### 8. Part 2에 대한 비판적 검토

#### (a) N+M은 정말 N×M보다 나은가 — 숨은 비용

"파이프라인 N×M개 → N+M개"는 깔끔하지만, 로그로 옮겨진 복잡도가 사라지는 건 아닙니다. 이동할 뿐입니다:

- **스키마 거버넌스 비용** — 중앙 로그는 모든 팀이 합의해야 하는 **공유 계약**이 됩니다. 계약 협상 비용은 팀 수에 비례해 증가합니다. 글은 Avro로 이를 해결한다고 하지만, 조직적 협상 비용은 기술로 없어지지 않습니다.
- **소비자 측 변환 중복** — 각 소비자가 자기 형태로 변환해야 하므로, "공통 변환"은 M개 소비자에 중복 구현될 수 있습니다.
- **디버깅 난이도** — 점대점 파이프라인은 어디서 깨졌는지 명확합니다. 로그 기반에서는 "생산자가 안 보냈나, 로그가 유실했나, 소비자가 못 따라잡나"를 매번 추적해야 합니다.

#### (b) 중앙 로그의 단일 장애점(SPOF) 성격

모든 데이터를 한 시스템에 넣으면, 그 시스템이 죽을 때 **회사 전체가 멈춥니다.** 글은 이 리스크를 정면으로 다루지 않습니다. 실무에서 Kafka 클러스터 운영은 전담 팀과 상당한 전문성을 요구하며, 이것이 2020년대에 관리형 서비스(Confluent Cloud, MSK, Redpanda Cloud)가 번성한 이유입니다.

#### (c) "생산자가 정제한다"는 조직적 이상론

정제 책임을 생산자로 옮기는 건 논리적으로 옳지만, **생산 팀에게는 그 일을 할 인센티브가 약합니다.** 자기 서비스의 기능 개발이 우선이고, 하위 소비자의 편의는 KPI가 아닙니다. 실제로 이 모델이 작동하려면 강한 플랫폼 팀의 게이트키핑이나 "데이터 계약(data contract)" 같은 조직적 강제 장치가 필요합니다. 2020년대의 **Data Mesh** 담론(도메인 팀이 데이터 프로덕트를 소유)은 이 글의 제안을 조직론으로 확장한 것이지만, 동시에 그 실행 난이도가 얼마나 높은지를 보여주기도 합니다.

#### (d) 이벤트 vs. CDC의 미묘한 차이를 뭉갬

글은 "DB changelog"와 "애플리케이션 이벤트"를 같은 로그 추상화로 묶습니다. 하지만 실무에서 둘은 성질이 다릅니다:

| | CDC (DB changelog) | 애플리케이션 이벤트 |
|---|---|---|
| 스키마 소유 | DB 스키마에 종속 → 내부 구현이 외부로 새어 나감 | 의도적으로 설계된 공개 계약 |
| 의미 | "행이 바뀌었다"(구현 수준) | "주문이 완료되었다"(도메인 수준) |
| 진화 | 테이블 리팩터링이 소비자를 깸 | 이벤트 계약을 유지하며 내부 변경 가능 |

CDC는 도입이 쉽지만(애플리케이션 수정 불필요) **DB 스키마를 전사 공개 API로 만들어버리는** 부작용이 있습니다. 이 긴장은 2026년에도 활발한 논쟁거리이며, Outbox 패턴이 그 절충안입니다.

> **관련 문서:** [`kafka/spring-kafka-consumer-vs-outbox.md`](../../kafka/spring-kafka-consumer-vs-outbox.md)가 이 Outbox 패턴을 다룹니다 — DB 트랜잭션 안에서 이벤트를 테이블에 쓰고, 그 테이블을 CDC로 흘려 "도메인 이벤트의 원자적 발행"을 얻는 방식입니다. 이 글의 이상(로그 = 단일 원본)을 실제 트랜잭션 경계 안에서 실현하는 실무 기법입니다.
