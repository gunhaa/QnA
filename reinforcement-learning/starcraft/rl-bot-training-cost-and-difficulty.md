# Pluto급 RTS 에이전트를 RL로 학습시키기 — 구현 난이도·하드웨어·소요 시간

> 조사 기준일: 2026-09-21. Pluto 자체의 학습 스케일은 **미공개**이므로, 공개된 유사 프로젝트 수치로 역산한 추정치를 명시해 구분한다.

## 쉬운 설명

컴퓨터가 스타를 스스로 배우려면 **수백만 판**을 둬야 해요. 그런데 진짜 어려운 건 "어떻게 배우냐"가 아니라 **"어떻게 그 수백만 판을 빨리 돌리냐"**입니다. 한 판에 20분이면 수백만 판은 수십 년이거든요. 그래서 게임을 수십 배속으로, 수백 개를 동시에 돌리는 공장을 먼저 지어야 합니다. 이 공장 짓는 게 전체 일의 절반이에요. 알고리즘 코드는 오히려 쉬운 편입니다.

### 1. 난이도의 실체 — 6가지 설계 난제

#### ① 환경 인프라 (가장 과소평가되는 부분, 전체 공수의 30~50%)

브루드워는 RL 친화적인 환경이 **전혀** 아니다.

- BWAPI는 **1.16.1 (32비트)** 에서만 동작한다. 리마스터에는 공식 API가 없다.
- 게임은 **단일 스레드**다. 병렬화는 "프로세스/컨테이너를 N개 띄우는" 방식뿐이다. 리눅스에서 돌리려면 Wine + 가상 디스플레이 스택이 필요하고, 이를 위해 [sc-docker](https://github.com/Games-and-Simulations/sc-docker) 같은 컨테이너 이미지가 존재한다.
- 크래시·데드락·타임아웃이 일상이다. 수천 개 인스턴스를 며칠씩 돌리려면 **자동 재시작, 경기 감시, 리플레이 수집, 결정론 보장**을 갖춘 오케스트레이션이 필요하다.
- 헤드리스(GUI 없음) + 속도 무제한으로 돌려야 하고, 16코어 CPU 벤치마크에서 **처리량은 물리 코어 수에서 포화**한다.

SC2가 공식 학습용 API(PySC2/SC2 API, 리플레이 포맷, 배속 실행)를 제공하는 것과 비교하면, BW는 출발선이 몇 달 뒤에 있다.

#### ② 관측·행동 공간 설계

이미지 픽셀을 그대로 넣는 방식은 RTS에서 비효율적이다. 현대적 접근은 **엔티티 기반**이다.

- **관측**: 유닛/건물마다 (종류, 체력, 위치, 상태, 쿨다운…) 피처 벡터 → 가변 길이 집합 → 트랜스포머/셀프어텐션으로 인코딩. 여기에 맵 공간 정보(미니맵 CNN), 자원·인구·업그레이드 같은 스칼라, 그리고 안 보이는 적 정보에 대한 **기억(LSTM/시퀀스 모델)** 을 결합한다.
- **행동**: "무엇을(which unit) / 어떤 행동을(action type) / 어디에·누구에게(target)"의 **구조화된 복합 행동**이다. 조합 폭발을 막기 위해 자기회귀적(autoregressive) 행동 헤드로 쪼개 순차 샘플링하는 것이 표준이다.
- **행동 빈도**: Pluto는 6프레임마다 1스텝(약 초당 4회 정책 평가), 내부 240 APM 제약. APM 제한은 "사람 같은 제약"이자 **행동 공간 축소** 수단이기도 하다.

이 설계는 논문을 읽어도 그대로 되지 않는다. 피처 하나 빠뜨리면 학습이 정체되고, 원인 규명에 수 주가 걸린다.

#### ③ 장기 지평 + 부분 관측

20분 게임은 24fps 기준 약 28,800프레임 = 6프레임 스텝으로 **4,800스텝**이다. 보상은 마지막의 승/패 ±1 하나. 여기에 전장의 안개(POMDP)까지 겹친다. 즉 **극단적으로 희소한 보상 + 긴 신용 할당 + 불완전 정보**의 3중고다. 대응책은 중간 보상 설계(자원 채취, 유닛 교환비), 가치 함수에 상대 정보를 추가로 주는 기법(AlphaStar의 학습 시 전체 관측 value baseline), 커리큘럼 등이다.

#### ④ 자가대국의 비정상성

상대도 같이 변하므로 학습 목표가 고정되지 않는다. 전략 순환(가위바위보)에 빠져 "특정 스타일에만 강한" 에이전트가 되기 쉽다. AlphaStar가 **리그 학습**(메인 + 메인 익스플로이터 + 리그 익스플로이터 + 과거 체크포인트 풀)을 도입한 이유다. 이 리그 관리 자체가 분산 시스템 설계 문제다.

#### ⑤ 분산 학습 인프라

표준 구조는 **actor-learner 분리**(IMPALA/SEED RL 계열)다. 수백~수천 개 actor가 게임을 돌리며 trajectory를 생성하고, learner가 GPU에서 배치 학습한다. 참고로 TStarBot-X는 144 V100 GPU + 13,440 CPU 코어 구성에서 **GPU 1장당 actor 70개(코어 2개씩)**, GPU당 210 fps 소비 속도로 돌렸다.

여기서 RTS 특유의 문제가 하나 더 있다. **actor도 추론(GPU)을 해야 한다.** Pluto 기준 1스텝 추론이 15ms이므로, 20분 게임 한 판은 추론만 4,800 × 15ms ≈ 72초다. 즉 배속 상한이 약 17배로 묶인다. 학습 중에는 추론을 배치로 묶어 GPU 한 장이 수십 게임을 서빙하는 구조(중앙 추론 서버)가 사실상 필수다.

#### ⑥ 평가와 디버깅

RL은 "버그인지 하이퍼파라미터 문제인지 학습이 덜 된 건지" 구분이 극도로 어렵다. 스타처럼 한 판이 긴 환경에서는 피드백 루프 한 번이 며칠이다. 고정 상대 봇 풀(McRave, Locutus, PurpleWave 등) 대비 승률, Elo 추적, 리플레이 자동 수집·요약 같은 **평가 파이프라인을 먼저** 만들어야 한다.

### 3. Pluto에서 역산할 수 있는 것

공개 정보(README, 릴리스)로부터 추론 가능한 사실:

- **추론 VRAM 2.5GB, 가중치 파일 약 1.2GB** → FP16 기준 수억 파라미터는 아니고, **수천만~1억 파라미터 안쪽**의 중형 모델로 보인다. LLM 기준으로는 아주 작다. 즉 **모델 크기가 아니라 경험량(환경 스텝)이 비용의 본체**다.
- **6프레임당 1스텝, 15ms/step** → 실시간 대비 추론이 무겁다. 학습 시에는 별도의 배치 추론 경로가 있었을 것이다.
- **릴리스 태그 `model v2247200`** → 학습 이터레이션/스텝 카운터로 보인다(224만). 스텝 1회당 배치 크기를 알 수 없어 총 경험량은 환산 불가.
- **저자 이력**: Vegard Mella는 Facebook AI Research의 TorchCraft/CherryPi 팀 멤버였다(CherryPi는 SSCAIT 2017-18 우승). 즉 **BW를 RL 환경으로 감싸는 인프라 경험을 이미 수년간 축적한 사람**이다. 이것이 "개인이 해냈다"의 실제 의미다 — 맨땅에서 시작한 개인이 아니라, 해당 분야 최고 수준의 인프라 경험자가 개인 프로젝트로 돌린 결과다.

> 따라서 "나도 GPU 한 장 사서 해볼까"의 답은: **알고리즘은 따라 할 수 있지만, 이 결과를 재현하려면 환경 인프라 경험이 알고리즘 지식보다 중요하다.**

### 4. 처리량 산수 (직접 견적 내는 법)

필요 경험량을 `G`판이라 하고, 한 판 평균 20분(실시간)이라 하자.

```
필요 실시간 = G × 20분
실제 소요   = 필요 실시간 / (배속 × 동시 게임 수)
```

- 헤드리스 BW는 봇 연산이 가벼우면 수십 배속이 나오지만, **신경망 추론이 배속을 지배**한다. Pluto 추론(15ms/step) 기준 배속 상한 ≈ 17배. 학습용 소형 모델·배치 추론이면 30~60배도 가능하다.
- 게임 1개당 CPU 코어 2개를 잡는다고 보면(TStarBot-X의 배치와 동일), **64코어 = 동시 32게임**.
- 예시: 배속 20 × 동시 32게임 = 실시간 대비 **640배**. 하루에 `640 × 24시간 / 20분` ≈ **46,000판**.
- 자가대국으로 풀게임 수준에 도달하려면 최소 **수백만 판** 단위가 필요하다고 보면, 위 설정으로 **수개월**이 나온다. 코어 수를 4배로 늘리면 기간이 1/4로 줄어드는 구조다(GPU 추론이 따라준다는 전제).

즉 예산 설계는 이렇게 뒤집어 하면 된다. **"몇 판이 필요한가 → 몇 배속으로 몇 개를 동시에 돌릴 수 있는가 → 그 CPU/GPU를 몇 달 빌릴 돈이 있는가."**

### 5. 현실적 로드맵 (개인/소규모 기준)

| 단계 | 내용 | 검증 기준 | 예상 기간 |
|---|---|---|---|
| 0 | 환경 래퍼 구축: BWAPI 연동, 헤드리스 병렬 실행, 크래시 복구, 리플레이 수집 | 1,000판 무중단 자동 실행 | 1~2개월 |
| 1 | 관측/행동 인코딩 + 랜덤 정책 파이프라인 | 스텝 처리량(FPS) 측정치 확보 | 2~4주 |
| 2 | **미니게임 RL** (일꾼 최적화, 소규모 교전 컨트롤) | 스크립트 베이스라인 초과 | 1~2개월 |
| 3 | 제한 풀게임 (종족 1개, 맵 1개, 빌드 고정) | 내장 AI·약한 봇 격파 | 2~4개월 |
| 4 | 자가대국 + 리그 도입, 종족/맵 확장 | 상위 스크립트 봇 상대 승률 | 6개월+ |
| 5 | 스케일업 (분산 actor, 중앙 추론 서버) | Elo 지속 상승 곡선 | 지속 |

단계 0~2에서 대부분이 포기한다. 여기서 막히는 이유는 RL 지식 부족이 아니라 **시스템 엔지니어링** 때문이다.

### 6. 비용 시나리오 (클라우드 기준 대략치)

| 시나리오 | 구성 | 월 비용 개략 | 비고 |
|---|---|---|---|
| 개인 워크스테이션 | RTX 4090/5090 1장 + 16~32코어 | 전기료 수준 (초기 300~500만원) | 미니게임·제한 풀게임까지. 시간으로 컴퓨트를 대체하는 전략 |
| 소규모 클러스터 | GPU 8장 + 128~256 vCPU (스팟) | 수백만~1천만원대 | 본격 자가대국 가능 구간 |
| 준-AlphaStar | GPU 64~144장 + 수천 코어 | 수천만~억 단위 | 기업/연구소 영역 |

#### "1인 프로젝트로 감당 가능한 금액인가" — 개략 추정

KataGo 사례(V100 27장 × 19일 ≈ 1.4 GPU-년 ≈ 약 12,000 GPU-시간)를 기준선으로 잡으면,

- **GPU**: 스팟/중소 클라우드 시세를 시간당 $0.4~1.5로 잡으면 12,000시간 ≈ **$5,000~18,000**
- **CPU**: 64~128 vCPU 스팟을 6개월 = 약 4,300시간, 시간당 $0.5~2 ≈ **$2,000~9,000**
- **자가 장비 대안**: RTX 4090/5090 1~2장 + 다코어 워크스테이션 ≈ **1,500만~3,000만 원 1회성** + 전기료

즉 **수천만 원 규모, 개인이 몇 년에 걸쳐 감당 가능한 범위**에 들어온다 — AlphaStar의 $3M과 두 자릿수 배 차이다. 단 이는 "시행착오 없이 한 번에 성공했을 때"의 학습 비용이고, 실제로는 실패한 실험 수십 회가 여기에 곱해진다. 그래서 **돈보다 인프라 경험과 실험 반복 속도가 실질적 진입장벽**이다. (위 수치는 공개 사례에서 역산한 개략치이며 Pluto의 실제 비용은 미공개다.)

CPU가 GPU보다 중요한 구간이 길다는 점이 RTS RL의 특징이다. 일반적인 LLM 파인튜닝 감각(“GPU만 있으면 됨”)으로 접근하면 견적이 크게 빗나간다. 또한 스팟 인스턴스로 CPU 풀을 구성하면 비용을 크게 낮출 수 있다(OpenAI Five도 preemptible 코어를 썼다).

### 7. 정리

- **알고리즘 난이도: 중** — PPO/IMPALA 계열은 공개 구현이 충분하다.
- **설계 난이도: 상** — 관측·행동 공간, 보상, 리그 구성은 도메인 감각이 필요하고 실패 원인 규명이 느리다.
- **인프라 난이도: 최상** — BW 특유의 32비트/단일 스레드/크래시 문제를 수천 인스턴스 규모로 길들이는 것이 실질적 진입장벽이다.
- **하드웨어**: 최소 GPU 1장으로 시작 가능하나, 풀게임 자가대국은 **CPU 코어 수가 1차 병목**. GPU 8장 + 수백 코어가 현실적 최소 본진 규모.
- **시간**: 경험자 기준으로도 인프라 포함 **1년 이상**을 잡아야 한다. Pluto도 저자의 수년간 축적 위에서 나왔다.
