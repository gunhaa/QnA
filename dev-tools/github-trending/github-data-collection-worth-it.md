# 직접 GitHub 자료를 모으는 것, 의미가 있을까? (API 직접 테스트해봄)

말씀하신 추측이 **API 테스트로 확인해보니 정확했어요.** 다만 "그래서 의미가 없다"는 아니고, 조건이 좀 달라요.

## 직접 확인한 결과

터미널에서 실제로 GitHub API를 두드려봤어요.

```
curl "https://api.github.com/repos/torvalds/linux"
→ stargazers_count: 245895  (딱 "지금 이 순간"의 숫자 하나만 줌)

curl "https://api.github.com/repos/torvalds/linux?at=2020-01-01"
→ stargazers_count: 245895  (날짜를 지정해도 그냥 현재값 그대로 반환 = 과거 조회 기능 자체가 없음)
```

→ **확인됨: GitHub REST API의 저장소 정보 엔드포인트는 "현재 시점 스냅샷 하나"만 주고, "2020년엔 스타가 몇 개였어?" 같은 시간여행 조회는 아예 지원 안 해요.** 이건 API가 부족한 게 아니라, 애초에 그런 기능이 설계되어 있지 않은 거예요 (마치 온도계가 "지금 온도"는 알려줘도 "어제 몇 도였는지"는 스스로 기억 안 하는 것과 같아요).

## 그럼 "과거 데이터"는 정말 아예 없나요? → 아니요, 다른 곳엔 있어요

여기서 중요한 반전이 있어요. **REST API엔 없지만, 지난번 소개한 GH Archive에는 2011년부터의 "별을 누른 순간들"이 이미 다 기록되어 있어요.**

- GH Archive는 GitHub에서 스타를 누르는 순간(`WatchEvent`)을 **실시간으로 계속 낚아채서 시간별 파일로 저장**해온 프로젝트예요. 2011년부터요.
- 즉 "리눅스 커널이 2019년 3월에 스타를 몇 개 받았는지"를 지금 당장 Google BigQuery로 질의하면 **바로 알아낼 수 있어요.** 이건 REST API가 아니라 이미 쌓여있는 로그 창고를 뒤지는 거예요.

## 그래서 "직접 모으는 것"이 의미 있는 경우 vs 없는 경우

| 상황 | 직접 모아야 할까? |
|---|---|
| **과거(예: 작년) 데이터가 필요함** | ❌ 의미 없음 — 이미 지나간 시간은 못 되돌려요. 대신 GH Archive/BigQuery로 이미 있는 과거 기록을 꺼내 쓰면 돼요. |
| **미래(오늘부터 쭉) 특정 저장소를 계속 관찰하고 싶음** | ✅ 의미 있음 — 내가 관심있는 몇 개 저장소만 콕 집어서, 실시간에 가깝게, 내가 원하는 주기(예: 10분마다)로, 내 서버/내 형식으로 쌓고 싶다면 직접 수집이 유일한 방법이에요. |
| **전체 GitHub을 다 커버하는 범용 아카이브를 새로 만들고 싶음** | ❌ 의미 낮음 — GH Archive가 이미 2011년부터 다 해놨어요. 바퀴를 다시 발명하는 셈. |
| **BigQuery 비용/속도가 부담되거나, 실시간성이 중요함** | ✅ 의미 있음 — BigQuery는 배치(시간 단위) 데이터라 "방금 일어난 일"엔 살짝 느려요. 진짜 실시간이 필요하면 직접 API를 짧은 주기로 찔러보는 게 나아요. |

## 한 줄 정리
말씀하신 대로 **GitHub API 자체는 과거 데이터를 절대 안 줘요(직접 테스트로 확인함).** 하지만 그렇다고 "직접 모으는 게 의미 없다"는 아니고: 이미 지나간 과거를 원하면 GH Archive를 뒤지는 게 정답이고, **지금부터 특정 대상을 내 방식대로 촘촘히 추적하고 싶다면 직접 모으는 것만이 유일한 방법**이라 여전히 의미 있어요.
