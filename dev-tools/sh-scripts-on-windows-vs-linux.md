# `.sh` 파일이 리눅스랑 윈도우에서 둘 다 돌아가는 이유 — 사실은 "같은 인터페이스"가 아니라 "번역기가 따로 하나씩" 있는 거예요

## 결론부터

**아니요, 같은 인터페이스로 처리하는 게 아니에요.** 윈도우는 원래 `.sh` 파일을 실행할 방법 자체가 없어요. `.sh`가 윈도우에서도 "그냥 되는 것처럼" 보이는 이유는, **윈도우 위에 리눅스 실행 환경을 흉내 내거나 아예 통째로 심어주는 "번역 계층(WSL, Git Bash/MSYS2, Cygwin)"**이 따로 설치돼 있기 때문이에요. 이 번역기들은 서로 구현 방식도, 완성도도 다르기 때문에 **같은 `.sh` 파일도 어떤 번역기로 돌리느냐에 따라 미묘하게 다르게 동작**할 수 있어요.

## 다섯 살에게 설명하듯

`.sh` 파일을 **"한국어로 쓰인 편지"**라고 생각해 보세요.

- **리눅스**는 원래부터 **한국어를 모국어로 쓰는 사람**이에요. 편지(`.sh`)를 받으면 첫 줄(셔뱅, `#!/bin/bash`)을 보고 "아, 이건 bash한테 읽어달라는 거구나" 하고 바로 이해해요.
- **윈도우**는 원래 **영어만 할 줄 아는 사람**이에요. 한국어 편지를 받아도 애초에 "이게 무슨 말이지?" 하고 못 읽어요. 윈도우는 파일이 뭘 하는 파일인지 **첫 줄 내용이 아니라 파일 이름 끝(`.exe`, `.bat`)**으로만 판단하거든요.
- 그래서 윈도우 컴퓨터에서 한국어 편지를 읽으려면, **한국어를 할 줄 아는 통역사를 따로 데려와야** 해요. 이 통역사가 바로 **WSL, Git Bash, Cygwin** 같은 것들이에요.
- 문제는 **통역사마다 통역 스타일이 조금씩 달라요.** 어떤 통역사(WSL)는 아예 한국 문화 전체를 통째로 옆방에 옮겨와서(가상의 리눅스 커널) 원어민처럼 완벽하게 통역하고, 어떤 통역사(Git Bash)는 영어를 하는 사람 머릿속에서 최대한 비슷하게 흉내만 내는 식이에요. 그래서 똑같은 편지를 줘도 통역 결과가 살짝씩 달라질 수 있어요.

## 기술적으로 풀어보면

### 1. 윈도우가 `.sh`를 원래 못 읽는 이유

리눅스·macOS 같은 유닉스 계열 OS는 파일이 실행 가능한지 아닌지를 **파일 내용의 첫 바이트(매직 넘버, magic number)**로 판단해요. 텍스트 스크립트의 경우 **셔뱅(`#!/bin/bash`) 줄**이 바로 그 역할을 해서, 커널이 "이 스크립트는 `/bin/bash`한테 넘겨서 실행해라"라고 알아서 처리해요.

반면 **윈도우는 파일이 실행 가능한지를 확장자(`.exe`, `.bat`, `.cmd`)로만 판단**해요. 윈도우 커널(NT 커널)에는 셔뱅 줄을 해석하는 기능 자체가 없어요. 그래서 `.sh` 파일을 윈도우 탐색기에서 더블클릭해도, 윈도우는 "이 파일을 어떤 프로그램으로 열어야 할지" 연결된 프로그램이 없으면 그냥 메모장으로 열거나 에러를 내요.

### 2. 그래서 등장하는 세 가지 "번역기" — 완성도가 다 달라요

| 방식 | 정체 | 특징 |
|---|---|---|
| **WSL (Windows Subsystem for Linux)** | 진짜 리눅스 커널(WSL2는 경량 가상머신 위에서 실제 리눅스 커널 구동) | 리눅스 배포판을 통째로 윈도우 옆에 심는 것에 가까워서, 완성도와 호환성이 가장 높음 |
| **Git Bash (MSYS2 기반)** | 윈도우 API 호출을 POSIX(유닉스 계열 표준 인터페이스) 호출처럼 보이게 감싸는 **에뮬레이션 레이어** | 가볍고 Git 설치할 때 같이 따라옴. 다만 진짜 리눅스가 아니라 "흉내"라서 세세한 동작이 다를 수 있음 |
| **Cygwin** | Git Bash와 비슷한 POSIX 호환 레이어(더 오래되고 더 방대한 유닉스 도구 세트 제공) | MSYS2/Git Bash의 뿌리가 된 원조 격 프로젝트 |

이 셋 다 "bash를 실행할 수 있게 해준다"는 결과는 같지만, **내부 구현 방식(진짜 커널 vs API 흉내)이 완전히 다르기 때문에 "같은 인터페이스"라고 부르기는 어려워요.** 실제로 이 대화가 이뤄지고 있는 이 환경 자체도 "PowerShell(윈도우 네이티브)"과 "Bash(Git Bash 기반 POSIX 셸)" 두 가지 도구를 각각 다른 문법 규칙으로 제공하고 있는데, 이게 바로 이 이중 구조를 보여주는 예시예요.

### 3. 실제로 다르게 동작하는 대표적인 지점들

- **경로(path) 표기법**: 리눅스식 통역기(WSL, Git Bash)는 `C:\Users\hwang`을 `/c/Users/hwang` 또는 `/mnt/c/Users/hwang`처럼 유닉스 스타일 경로로 바꿔서 보여줘요. 윈도우 프로그램과 값을 주고받을 때 이 경로 변환 과정에서 어긋나는 버그가 자주 나요.
- **줄바꿈 문자(line ending)**: 윈도우 텍스트 편집기(메모장 등)는 줄바꿈을 `CRLF`(`\r\n`)로 저장하는데, 리눅스는 `LF`(`\n`)만 써요. 윈도우에서 편집한 `.sh` 파일을 그대로 리눅스나 WSL에서 실행하면, 셔뱅 줄이 `#!/bin/bash\r`처럼 눈에 안 보이는 `\r`이 붙어서 **"해당 인터프리터를 찾을 수 없다"는 에러**가 나는 경우가 흔해요. (`dos2unix` 같은 도구로 변환해줘야 함)
- **실행 권한(permission)**: 리눅스는 `chmod +x script.sh`로 "실행 가능" 표시를 파일 자체에 저장하는데, 윈도우의 기본 파일 시스템(NTFS)에는 이 개념 자체가 없어요. WSL이 NTFS 위에 있는 파일에 대해 실행 권한을 어떻게 흉내 내느냐에 따라 동작이 달라질 수 있어요.
- **성능**: WSL2는 실제 리눅스 커널이 가상머신 위에서 도는 거라 대체로 네이티브에 가까운 성능을 내지만, 윈도우 파일 시스템(NTFS)에 있는 파일을 WSL에서 접근할 땐 그 사이의 다리를 건너야 해서 느려지는 경우가 있어요. Git Bash는 애초에 가상머신이 아니라 가벼운 편이지만 일부 유닉스 전용 기능은 아예 지원을 못 해요.

### 4. 그래서 "같은 스크립트인데 결과가 다르다"가 실제로 일어나요

같은 `.sh` 파일이라도:
- Git Bash에서는 되는데 WSL에서는 경로 문제로 안 되거나,
- 리눅스 서버에서는 되는데 Git Bash에서는 특정 유닉스 전용 명령어(예: 심볼릭 링크 관련, 프로세스 시그널 관련)가 없어서 에러가 나거나,
- 윈도우에서 편집만 하고 실행은 리눅스에서 했더니 줄바꿈 문제로 셔뱅이 깨지는 경우가 생겨요.

즉 `.sh` 파일 자체는 "이식 가능한 텍스트"일 뿐이고, **그 텍스트를 실제로 실행 가능하게 만들어주는 "통역 환경"이 플랫폼마다 별도로 존재하며, 그 통역 환경들이 서로 100% 동일하지 않다**는 게 핵심이에요. [`bash-script-vs-shell-and-common-confusions.md`](bash-script-vs-shell-and-common-confusions.md)에서 다룬 "`#!/bin/bash` vs `#!/bin/sh`"처럼 리눅스 배포판끼리도 셔뱅 해석이 다른데, 윈도우까지 끼면 그 편차가 한 단계 더 커지는 셈이에요.

## 요약

| 질문 | 답 |
|---|---|
| 윈도우가 `.sh`를 원래 이해하나? | 아니요. 셔뱅 해석 자체가 윈도우 커널엔 없음 |
| 그럼 어떻게 실행되나? | WSL(진짜 리눅스 커널) / Git Bash·Cygwin(POSIX 흉내 레이어) 같은 별도 통역 계층을 통해서 |
| 이 통역 계층들은 서로 같은가? | 아니요. 구현 방식(가상 커널 vs API 에뮬레이션)이 다르고, 경로·줄바꿈·권한·성능에서 미묘하게 다르게 동작함 |
| 그래서 정말 크로스플랫폼인가? | "텍스트 파일로서는" 이식 가능하지만, "실행 환경으로서는" 플랫폼별 통역기 품질에 의존하는 조건부 호환임 |
